## いつ使うか

- 帳票が運用のデータベースを遅くし始めたときに移します。これは materialized-view の競合ではなく、その次の段階です。実体化ビューはデータをすでに抱えている格納庫の中か傍らで、分かっているクエリひとつを先に計算しておく方法で、帳票が数を増し、読めなくなり、許可を求めない人たちが書き始めた時点でもう答えではなくなります。分析の仕事をまるごと自分のデータベースへ移すことは、競合を配給するのではなく取り除く側の手です。
- そもそも結合するように設計されたことのないシステムをまたいで問う必要があるときに建てます。注文はあるサービスのデータベースに、決済は別のサービスに、カタログはさらに別のサービスに住んでいて、月ごとの分類別の売上は、そのどれも単独では答えられない一文です。ウェアハウスは、それらの抜き出しが共通の次元へそろえられる場所であり、そうしてはじめて結合が成り立ち、走らせるたびに同じ意味を持ちます。
- 面白い問いが履歴の全体を走査するときに建てます。趨勢もコホートも定着の曲線も前年との比較も、何年ぶんもの行を読みます。列指向の分析の格納庫が狙って作られた仕事であり、行指向の運用の格納庫が最も苦手とする仕事です。運用のインスタンスでは何分もかかりバッファプールを押し流すそのクエリが、向こう側ではありふれた一件です。
- スキーマを問いに合わせて建て直す値打ちがあるときに建てます。正規化された運用のモデルは書き込みが安く正しくなるように形づくられていて、事実と次元からなるスタースキーマは、分析する人が六つの表の結合なしに問いを言い表せるように、そしてエンジンが要らないものを刈り取れるように形づくられています。その組み直しに値する場所なら、いま話しているのはウェアハウスですし、そうでないなら読み取りの複製やビューでまだ足りることもあります。

## 注意点

- 実時間ではありませんし、取り込みの周期はこちらが公表すべき性質です。数字は最後に成功した取り込みのぶんだけ古いので、どのダッシュボードでも値の隣に新しさを書き、消費する側のチームとの約束にそれを明記し、終わらなかった取り込みに警報を掛けて、昨日の合計が黙って今日の席に座ることを防いでください。時刻の付かない古い数字は実時間として読まれますし、ウェアハウスはそうやって信頼を失います。
- 本体はモデリングと取り込みの流れであって、買ってくる製品ではありません。エンジンを選ぶのは半日で済みます。三つのシステムが食い違うときに顧客とは何かを決め、遅れて届いた行をどうするかを決め、先週の火曜に変わった次元をどう扱うかを決め、やり直しても同じ結果が出るようにするのに、案件の残り全部がかかります。流れとモデルに予算を置き、エンジンの選択はこの計画で最もつまらない決定として扱ってください。
- BI の道具を運用のデータベースへ直につなぐのは、利息の付く近道です。最初のダッシュボードまではうまくいき、次に誰かが上限のないクエリを書き、ロックを抱え、二度と読まれない行でバッファプールを満たすと、事故は帳票を走らせたチームのものなのに、呼び出しはそのサービスを預かるチームに鳴ります。ウェアハウスがまだないなら、当座の手当ては直接の接続ではなく、自分の資源の上限を持つ読み取りの複製です。
- ウェアハウスは写しであって、決して記録の原本ではありません。訂正は上流の運用の格納庫で行い、下へ流れてきます。ウェアハウスの中だけで直した値は業務と食い違う数字で、取り込み直しても再現しません。元から建て直せる力を保ってください。建て直せないウェアハウスは、その履歴をもう検証できないウェアハウスです。

## .NET では

- ここでのアプリケーションはほぼ常に読み取り専用の消費者であり、それが健全な関係です。サービスは自分の運用の格納庫へ書き、流れがデータを渡し、帳票の端点や BI の道具が別の接続文字列と別の資格情報と自前の資源の管理のもとでウェアハウスを読みます。顧客に向いた機能の要求の経路から、ここへ手を伸ばすものが何ひとつあってはいけません。
- Azure では Microsoft Fabric のウェアハウスとレイクハウス、そして Synapse の SQL の面がマネージドの行き先で、`Microsoft.Data.SqlClient` や Dapper がすでに話しているのと同じ表形式の手順の上で T-SQL を話します。つまりダッシュボードの端点はふつうの接続の上のふつうのクエリで、面白い違いはクライアントのライブラリーではなくその周りの配管にあります。規模の調整も別、費用も別、資格情報は運用のデータへ何の権限も与えません。
- データを渡す部分にこそ本当の選択肢があります。予定された抜き出しは最も単純で最も粗いものです。変更データキャプチャや、運用のサービスがすでに発行している event-stream は、はるかに短い周期の連続した供給をくれます。データベース全体の複製は用意こそ簡単ですが、分析のモデルではなく運用のモデルをそのまま写すので、組み直しの宿題は手つかずで残ります。約束した新しさと、変換のうちどれだけを続けて走らせたいかで選んでください。
- ウェアハウスの表の設計は、運用の格納庫とは別のところに気を配ります。日付で分割しておくことが、クエリに五年ではなくひと月だけを触らせる仕掛けですし、列指向の並びのせいで、取引の表に当てていた索引の規律はほとんどそのままは移ってきません。物理の並びは想定する走査に合わせて設計し、本物のクエリが届いたら一度書き直すつもりでいてください。
