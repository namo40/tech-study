シーンの第二段階はトークンを分解します。すると、ドットで区切られた base64 の断片が三つ出てきます。最初はヘッダーで、わざと小さく退屈に作られています。何のアルゴリズムで署名したか、どの鍵かだけです。二つめはペイロード、つまりクレームで、この流れのなかで実際に読まれるのはここです。三つめは前の二つに対して計算された署名で、鍵を持っている者だけが作れる唯一の部分です。

パネルが解錠されるのではなく、ただ開くところがこの段階の言いたいことです。Base64 は転送用のエンコードで、トークンが URL やヘッダーやコピー貼り付けに耐えるように選ばれています。戻すのに鍵も許可もいりません。トークンをデコーダに貼り付けたことのある人は、すでにこれを確かめています。ですから署名は秘匿ではなく、もともとそのつもりもありません。署名は、いま手にしているバイト列が発行者の作ったバイト列であることを証明するだけで、誰が手にしているかについては何も証明しません。bearer の資格情報が持つ性質を内側から述べると、ちょうどこうなります。

ここから、してはいけないことの短い一覧が出てきます。クレームに秘密を入れないこと。クレームはトークンを持つ者すべてに公開されていて、利用者本人も、そのブラウザ拡張が読めるものも含みます。取りに行きたくないデータのキャッシュとして JWT を使わないこと。トークンはリクエストごとに一緒に運ばれるので、2 キロバイトに膨らんだペイロードは呼び出しごとの 2 キロバイトであり、いつかぶつかるヘッダーサイズの上限でもあります。そして「きれいにデコードできた」を検証とみなさないこと。攻撃者が自分で書いたトークンでもデコードはできます。

検証とは署名と、その周りにある登録済みクレームのことで、アルゴリズムは知らされる対象ではなく確かめる対象です。ここでの有名な失敗は、ヘッダーの `alg` を読んでそのまま信じたライブラリでした。おかげで攻撃者は `alg` を `none` にしたり、RSA のトークンを公開鍵で署名した HMAC に格下げしたりできました。いまのライブラリはどちらも既定で拒みますし、その状態を保つ方法は、届いたものをそのまま受け入れるかわりに受け入れるアルゴリズムを固定することです。

対称か非対称かが、誰が発行できるかを決めます。`HS256` は共有の秘密を一つ使うので、トークンを検証できるサービスは作ることもできます。一つのアプリケーションの中なら問題ありませんが、二つのチームが関わった時点で悪い選択になります。`RS256` と `ES256` は秘密鍵で署名し、よく知られた JWKS エンドポイントに公開された公開鍵で検証するので、百の API が確認できる一方、発行できるのはちょうど一つのサービスだけです。鍵の入れ替えはそのエンドポイントの性質になります。発行者が新しい鍵を古い鍵と並べて公開すれば、検証する側は `kid` で両方を拾い、古い鍵で署名されたトークンが尽きたところで古い鍵を下げます。

最後に知っておきたいのは、自己完結であることの代償です。検証に発行者への呼び出しがいらないということは、発行のあとで発行者が知った事実は、すでに飛び立ったトークンには届かないということです。セッションの終了、ロールの剥奪、端末の認証解除、そのどれも署名を変えません。この形式が結んだ取引がそれで、抜け道はシーンの第四段階が見せる二つだけです。窓が問題にならないほど短い寿命と、問題になるときのために id で突き合わせる拒否リストです。
