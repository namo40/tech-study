## いつ使うか

- すべてのデプロイは戻り道を 1 本ずつ持つべきで、その道は障害の最中ではなくデプロイの前に用意しておきます。前のリビジョンがまだそこにあり、まだ動かせるということです。プラットフォームにリビジョン履歴を残し（Kubernetes Deployment の `revisionHistoryLimit`、スロット入れ替えで残る前のスロット）、イメージタグを使い回さずに `v1.4.2` が先週と同じものを指すようにし、設定もコードと一緒にバージョン管理して、古いバイナリが試験を受けたときの設定に再会できるようにします。
- 新しいリリースが目に見えて悪いのに理由がまだ分からない、その瞬間に使います。ロールバックは診断ではなく応急処置です。ログを読む間にエラーバジェットを買い戻す作業です。悪いリビジョンはその後も棚に残っていて、診断はそこで行います。
- プラットフォームが代わりにできる場面では、プラットフォームにつなぎます。ヘルスで門を作ったロールアウトは、失敗したリリースが艦隊全体に届く前に止まり、一部のプラットフォームでは人の手を借りずに元へ戻します。それがこのページのいちばん安い形です。見張っていた何かが、数秒で自動的に戻り道を選ぶのです。
- 段階的デリバリーと二者択一にせず、組み合わせて使います。カナリアは悪いリリースを見る人数を絞り、ロールバックは見る時間を絞ります。両方あって初めて被害範囲が 2 つの軸で抑えられ、どちらか一方が他方の代わりにはなりません。
- バックアップを点検するように、ときどき実際にやってみます。試したことのない戻り道は計画ではなく願望であり、訓練中に見つかった失敗はただです。決断した瞬間から古いリビジョンがトラフィックを受けるまでの時間を測り、その値を独立したサービスレベル目標として扱います。

## 注意点

- データは戻りません。20 分動いていたリリースは自分の好きな形式でレコードを書いており、ポインターが後ろへ動いてもそのレコードが書き直されるわけではありません。スキーマ変更を拡張から出す理由がこれです。新しい列を足し、古い列を残し、両方を扱うコードを配備し、古い形式を必要とするリビジョンが完全にいなくなってから初めて縮小します。隣り合うリビジョン同士が互いの記録を読めることが条件で、そうでなければ戻り道は正確に必要な瞬間に閉じています。
- デプロイを戻すことと、データベースマイグレーションを戻すことは別の動作で、2 つを 1 つの動作にまとめるのが、悪い午後を悪い 1 週間に変えるやり方です。コードを先に、単独で戻し、スキーマはデータを目の前に置いて別に判断します。コマンド 1 つで両方やりますという道具は、圧力の下にいる人の代わりに取り返しのつかない決定を下しますと言っているのと同じです。
- あるマイグレーションには正直な逆方向がありません。列を落とす、型を狭める、2 行を統合する。こうした変更の down スクリプトは形を作り直せるだけで、値は戻せません。レビューの場でそれを口に出し、答えが「バックアップから復元するしかない」であれば、それがそのマイグレーションの本当の復旧計画です。その計画はマイグレーションが出る前に書いておくものであって、後から見つけるものではありません。
- 副作用も戻りません。出て行ったメールは出たままで、立った請求は誰かの明細に載っており、下流がすでに処理した Webhook は、こちらが制御していない世界を変えてしまいました。ここに答えるのは補償です。なかったことにする取り消しではなく、先の行為を打ち消す新しい行為です。返金は 2 件目の取引で、顧客は 2 件とも見ています。
- 変更が機能フラグの後ろにあるなら、フラグを切るほうが安いロールバックです。速く、範囲が狭く、何も配備しないので、同じリリースに乗った他の修正はそのまま残ります。デプロイ単位のロールバックは、スイッチの後ろにないコードに欠陥があるとき、あるいはスイッチ自体が壊れているときに使います。
- 悪いリビジョンは消さないでください。それが証拠であり、急いで作ったホットフィックスで上書きすると、実際に何が起きたのかの唯一の写しが失われます。ポインターだけを戻し、イメージとログはそのままにして、もう燃えていないシステムで診断します。
- 戻すこと自体にも危険はあります。古いリビジョンは今日のデータも、今日のトラフィックの形も、いまのスキーマも見たことがなく、新しいリリースがたまたま覆い隠していた自分のバグを抱えているかもしれません。たいていはより安全な賭けですが、それでも本番システムへの変更です。

## .NET では

Kubernetes では戻り道はコマンド 1 つで、それが成り立つのはプラットフォームが古い ReplicaSet を残しておいたからです。

```bash
# 棚に何があるかを見ます。この一覧が空にならないだけの履歴を残します。
kubectl rollout history deployment/checkout

# ポインターの移動です。ビルドはなく、ノードにあるイメージは取り直しもしません。
kubectl rollout undo deployment/checkout

# 直前の版が欲しい版でないときは、良いと分かっているリビジョンへ直接行きます。
kubectl rollout undo deployment/checkout --to-revision=7
```

Azure App Service では同じ動作がスロットを戻す入れ替えになり、どちらのプラットフォームでも速い理由は、何も作り直さないからです。`revisionHistoryLimit` は意図を持って決めます。低すぎると必要なときに棚が空で、高すぎると誰も二度と指さない ReplicaSet を抱え続けることになります。

データベース側は、マイグレーションが出る前に down スクリプトを作って読んでおきます。

```bash
# ロールバックが実際に流す SQL です。誰も圧力を受けていないうちに確認します。
dotnet ef migrations script AddDiscountColumn PreviousMigration --output down.sql
```

```csharp
// 破壊的な Down は、Up が消したものを戻せません。戻せるふりをせずにそう書いて
// おけば、復旧計画が復元であることを全員が分かります。
protected override void Down(MigrationBuilder migrationBuilder)
{
    throw new NotSupportedException(
        "DropColumn(LegacyTotal) is lossy. Recovery for this migration is a " +
        "point-in-time restore, not a down script.");
}
```

`dotnet ef database update <PreviousMigration>` がそのスクリプトを流しますが、これは `kubectl rollout undo` とは別の決定です。まずコードを処理します。そのうえで悪いリビジョンが何を書いたかを見て、それを目の前に置いてスキーマを判断します。

あとは、その道が存在するように前もって整えるだけです。本物の readiness probe にロールアウトを結び付けて壊れたリリースが艦隊全体を占めないようにし、振る舞いが変わる変更の前には機能フラグを置いていちばん速い道がスイッチを切ることになるようにし、判断のきっかけになる指標にアラートを掛けて、その判断が 10 分後ではなくエラー率と同じ瞬間に届くようにします。
