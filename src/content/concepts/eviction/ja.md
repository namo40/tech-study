## いつ使うか

Eviction はオンにする機能ではありません。上限のあるキャッシュはすべて追い出しをしますし、上限のないキャッシュは行儀のよいメモリリークにすぎません。ですから問いは追い出しが起きるかどうかではなく、ポリシーを選んだか、サイズを選んだか、そして項目が去るときに何を払うのかを知っているか、です。

- 上限のあるキャッシュを見るときのレンズとして読みます。シーンの六つの枠が上限で、その下の明るさの段がポリシーです。上限がいくつで、どの項目が最初に出ていくかを言えるなら、二つの決定をどちらも下しています。言えないなら、ランタイムが代わりに下しています。
- トラフィックは変わっていないのにヒット率が下がったときに取り出します。読み取りの 90% に答えていたキャッシュが 60% しか答えなくなったなら、たいていは問いが変わったのではなく答えを持っている量が減ったのであり、原因は項目が大きくなったか、キー空間が広がったかのどちらかです。どちらも遅延より先に追い出しの数値に現れます。
- ヒット率と追い出し数は別々にではなく、必ず並べて見ます。ヒット率だけでは冷たいキャッシュと過熱したキャッシュを区別できず、追い出し数だけでは健全な回転ともう収まらなくなった作業集合を区別できません。二つを並べれば区別できます。ヒット率が安定していて追い出しが多いなら受け入れられる回転で、ヒット率が下がりながら追い出しが多いなら、誰も二度読まない項目に予算を使い切っています。
- 一つのキャッシュが複数の種類の項目を持った瞬間から真剣に見ます。セッションの塊、描画された断片、参照用のテーブルは、同じ辞書を共有していること以外に共通点がなく、ポリシーが一つしかなければ、最も大きく価値の低いものが最も小さく価値の高いものを平然と押し出します。優先順位と項目ごとのサイズがあるのは、まさにこの場合のためです。
- 上限を上げる前に見ます。サイズを二倍にして稼げる時間は、作業集合のうち欠けていた分に比例し、その分は二倍にはるかに届かないことが多いのです。圧力が答えの種類の数ではなくキーのカーディナリティから来ているなら、キャッシュが大きくなっても重複が増えるだけで、ヒット率はほとんど動きません。
- 古い値の問題を直すために使ってはいけません。間違っている項目に必要なのは無効化か TTL です。追い出しは何の問題もなく正しい項目を消しますし、消す理由は誰かがそれを欲しがったかどうかとまったく関係がありません。

## 注意点

- `SizeLimit` のない `MemoryCache` は、マシンが悲鳴を上げるまで無限です。既定の上限がないので項目は積み上がり続け、それを減らすのは失効か、GC のメモリ圧力が呼ぶ圧縮だけです。圧縮は遅れて来て、選ぶべきだった項目ではなくキャッシュの 5% から 10% をまとめて持っていきます。上限を決めることが、追い出しを事故からポリシーに変えます。
- サイズには単位がなく、サイズを付けない項目が一つあるだけで全員分の上限が壊れます。`SizeLimit` はアプリケーションが `Size` の意味として決めたものを数えます。バイトでも行数でも項目あたり 1 でもよく、一貫していれば十分です。ただし上限が有効な状態でサイズなしに追加すると例外になり、それはたいていヘルパーを迂回したコード経路で見つかります。単位を一度決めてオプションのファクトリに入れ、呼び出し側ではサイズを指定しないでください。
- LRU は走査に弱いのです。大きなコレクションを一度なめる処理はすべてのキーをちょうど一回ずつ触り、その一回が一日かけて築いた作業集合より新しくなるので、走査は価値あるものをすべて追い出したあと自分自身も追い出します。バックグラウンドの処理やレポート、管理画面がホットパスのキャッシュするデータをさらっていくなら、その処理には別のキャッシュを与えるか、先に負ける低い優先順位を与えるか、そもそもキャッシュを与えないことです。
- 追い出しは失効ではなく、二つを混ぜると両方向にバグが出ます。TTL は「まだ正しいか」に答え、追い出しは「席があるか」に答えます。書いた一秒後の項目が追い出されることもあれば、古い項目が TTL の許す間ずっと触られずに座っていることもあります。サイズ上限を鮮度の仕組みとして使わないでください。TTL がメモリを縛ってくれると仮定してもいけません。
- キーのカーディナリティは、誰も予算に入れない掛け算です。キャッシュは異なる答えごとではなく異なるキーごとに項目を一つ持ちます。ですからリクエスト識別子や並び順の定まらないクエリ文字列、精度そのままのタイムスタンプを含む vary-by の選択は、一つの答えを、それぞれ一度しか読まれない何千もの項目に変えます。シーンの三段目がまさにこれで、直す場所はいつもサイズではなくキーです。
- 追い出しコールバックは事後に走り、拒否権を持ちません。事後追い出しコールバックはフックではなく通知です。項目が消えたあとしばらくしてスレッドプールのスレッドで走り、容量だけでなく失効でも同じように呼ばれ、その中で重い処理をすれば追い出しを引き起こしたまさにそのトラフィックと競合します。理由を読み、数え、それ以外のことはしないでください。

## .NET では

- 上限を決め、すべての項目にサイズを付けます。上限のあるキャッシュを立てる作業はこれで全部で、二つの側が数字の意味に合意している必要があります。

```csharp
builder.Services.AddSingleton<IMemoryCache>(_ => new MemoryCache(new MemoryCacheOptions
{
    SizeLimit = 1024,
    CompactionPercentage = 0.2,
}));

// Size は SizeLimit と同じ、こちらが決めた単位です。ここでは項目一つが 1 です。
cache.Set(key, value, new MemoryCacheEntryOptions
{
    Size = 1,
    SlidingExpiration = TimeSpan.FromMinutes(10),
});
```

- `CacheItemPriority` がシーンの pin にあたります。`Low`、`Normal`、`High` はキャッシュが圧縮するときに誰が先に出るかの順序を決め、`NeverRemove` は項目をポリシーの手の届かない場所に置きます。不滅を約束するわけではなく、明示的な `Remove` や失効はそのまま適用されますが、容量による圧力は他のすべてを先に空にします。なければ障害になる少数の項目に使うとよいでしょう。

```csharp
var options = new MemoryCacheEntryOptions
{
    Size = 1,
    Priority = CacheItemPriority.NeverRemove,
};
```

- 事後追い出しコールバックを登録して理由を数えます。`EvictionReason.Capacity` はサイズ上限がこの項目を選んだという意味で、`Expired` と `TokenExpired` は時間切れ、`Removed` と `Replaced` はこちらがやったことです。四つの違う物語であり、カウンター一つでは区別できません。

```csharp
options.RegisterPostEvictionCallback((key, value, reason, state) =>
{
    evictions.Add(1, new KeyValuePair<string, object?>("reason", reason.ToString()));
});
```

- 出力キャッシュでは vary-by がそのままキーなので、ポリシーの問題もそちらに移ります。`SizeLimit` と `MaximumBodySize` が保存領域を縛り、`SetVaryByQuery` や `SetVaryByHeader`、`VaryByRouteValue` を一つ足すたびに、その中で競合する項目が掛け算で増えます。クライアントが自由に決めるヘッダーで varying するポリシーは、キー空間が無限でサイズが有限なキャッシュであり、両方の悪いところだけを集めたものです。

```csharp
builder.Services.AddOutputCache(options =>
{
    options.SizeLimit = 100 * 1024 * 1024;
    options.AddPolicy("catalogue", policy => policy
        .Expire(TimeSpan.FromMinutes(5))
        .SetVaryByQuery("page", "sort"));
});
```

- `HybridCache` は分散キャッシュの前に小さなプロセス内キャッシュを置きますが、メモリ圧力で追い出しが起きるのはローカル側だけです。ふつうはそれが望みの姿です。近いキャッシュは作業集合で、遠いキャッシュは保存場所だからです。ただしローカルの追い出しは分散側のヒット率には見えないので、どちらが過熱しているかを言うには二つの層それぞれにカウンターが要ります。
- 分散の層では、ポリシーはこちらのものではなくサーバーのものです。Redis は自分の `maxmemory-policy` に従って追い出しますし、キーの大半に TTL がないとき `allkeys-lru` と `volatile-lru` はまるで違うふるまいをします。後者は追い出しを拒み、代わりに書き込みを失敗させ始めます。アプリケーションが自分のキャッシュについて何を信じていても、実際の上限を握っているのはサーバーです。
