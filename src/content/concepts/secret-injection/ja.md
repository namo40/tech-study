## いつ使うか

- コンテナーが実際に必要とする資格情報、つまり接続文字列、API キー、証明書、署名材料のすべてを、ビルドに書き込む代わりに起動時に配達するときに使います。判断はとても簡単です。誰かがイメージを取得してその中からシークレットを読み出せるなら、そのシークレットを守っていたのは「誰も気づかないだろう」という期待だけでした。公開レジストリ、漏れた pull トークン、一度でも `docker save` を実行したノート PC の前で、その期待は残りません。
- 同じ成果物が複数の環境で動く必要があるときに使います。一度ビルドして違うものを注入するというのが、このパターンが存在する理由そのものです。1 つのイメージがステージングにも本番にもそのまま行き、起動時に別々の値を受け取るので、テストしたものと出荷したものがビット単位で同じになります。環境ごとにイメージを分ける道を選ぶと、ビルドの組み合わせが増え、いちばんテストされていないイメージが本番のイメージになります。
- ローテーションが再ビルドであってはならないときに使います。レイヤーに住む資格情報は、新しい成果物を作ってそれを動かすすべての場所を再デプロイしない限り置き換えられないので、ローテーションがリリースになってしまいます。配達が起動時に起きるようになれば、ローテーションはストア 1 か所の変更と、多くても再起動 1 回です。四半期ごとに抱える案件と、ふつうの火曜日との差がここで分かれます。
- アクセスをワークロードごとに絞る必要があるときに使います。アクセスリストを持つストアは、この資格情報はこの 2 つのワークロードにだけ行き、他のどこにも行かないと言えますし、それをレビュアーが読める場所に書いておけます。イメージに焼き込まれたものは範囲を絞る方法がまったくありません。イメージを持つ人が値を持ちます。
- **シークレットがまったくない方が優れています。** プラットフォームがワークロードを保証できる場所ではそうです。ワークロード ID は資格情報を配達する代わりに消し去りますし、存在しない資格情報は漏れもせず、都合の悪いときに期限切れにもならず、持ち主も要りません。注入は、それでも存在しなければならない資格情報のためのものです。サードパーティの API キー、ベンダーがフェデレーションしてくれないデータベースのパスワード、古いシステムなど、今はまだその大半がここに当てはまりますが、年ごとに減っていきます。
- **開発者のマシンに本番のシークレットを置く抜け道としては使わないでください。** ローカル開発は自分の値を別に持ちます。リポジトリの外にあるユーザーシークレットストア、ローカルエミュレーター、捨ててよいアカウントといったものです。ローカルでアプリを動かす唯一の方法が本番の資格情報を握ることなら、このパターンは導入されたのではなく飾られただけです。

## 注意点

- 環境変数は横に漏れますし、漏れる経路はどれも平凡です。子プロセスが環境全体を受け継ぐので、シェル経由で呼び出すものすべてが値を受け取ります。クラッシュダンプが値を含みます。設定を出力する診断エンドポイントやエラーページが値を出力します。プラットフォームによってはプロセス一覧に現れます。どれも珍しいことではなく、環境とはもともとそのためにあるものです。価値の高いシークレットはマウントされたファイルに置くか、起動時にクライアントで取得し、環境変数には、漏れても深刻というより煩わしい程度の値だけを残す方が安全です。
- マウントされたシークレットは条件付きでその場で更新され、それでもアプリケーションが気づく必要があります。ボリュームを `subPath` でマウントしているとまったく更新されませんし、更新される場合でも変更が届くのは kubelet の同期周期より速くはならないので、ローテーションは即時ではなく結果整合です。CSI Secrets Store のマウントは、ドライバーの導入時にローテーションを有効にした場合にだけ回ります。そのうえでアプリケーション側の半分が来ます。ファイルは動いているプロセスの下で入れ替わり、誰も代わりに開き直してはくれません。ファイルを監視して読み直すか、次に読むときに反映される方式を受け入れたうえで、古い値が通らなくなる前にその読み取りが起きるようにします。起動時にシークレットを一度だけ読んで静的フィールドに入れるアプリは、ローテーションするファイルを凍り付いた環境変数に戻してしまったのと同じです。
- マニフェストの中の base64 はエンコーディングであって暗号化ではありません。バイナリの値がテキスト形式でも壊れないようにするためのもので、守ってくれるものは何もありません。base64 が入ったマニフェストは、平文が入ったマニフェストとまったく同じように扱えば十分です。ストアの保存時暗号化を有効にし、読み取りを RBAC で塞ぎ、鍵が別の場所にある仕組みで封印や暗号化をしていないマニフェストはバージョン管理に入れないでください。
- アクセスリストはワークロード単位で絞ります。クラスターのすべてのポッドが読めるストアは、手順が増えただけの焼き込まれたシークレットです。ワークロード 1 つが侵害されたときの影響範囲が、また全体に戻ってしまうからです。シークレットごとにリストを 1 つ、そのリストにはそれを必要とするワークロードだけを書く。それがストアと共有フォルダーを分けるすべてです。ロールの割り当てをレビューするのと同じように、リストもレビューする値打ちがあります。
- 値はログに残さず、バージョンを残してください。障害を振り返るたびに、どのワークロードがどのバージョンを握っていたのかを知りたくなりますが、その問いは、シークレットをログの 1 行にも、トレース属性にも、メトリクスのラベルにも、例外メッセージにも入れずに答えられます。マスキングのフィルターは 2 番目の防御線であって 1 番目ではありません。値はそもそもロギングの呼び出しまで届かないべきです。
- リポジトリには参照をコミットし、生の値はコミットしないでください。リポジトリは、シークレットが複製され、ミラーされ、永久に残ることが保証されている唯一の場所です。そこに入れてよいのはストアの項目名、封印または暗号化された塊、`secretRef` を指すマニフェストといったポインターで、値の方はストアに入ります。すでに clone されて出ていったものは、履歴を書き換えても漏れていない状態には戻りません。
- 配達は認可ではありません。注入は、このワークロードがどうやって資格情報を受け取るかに答えるだけで、受け取ってよいのかには答えません。2 つの判断は別々の場所で下されるもので、尋ねてきたものすべてにすべてのシークレットを渡すストアは、どちらにも答えていません。

## .NET では

`IConfiguration` はまさにこの形のために作られています。順序のあるソースを重ね、後から来たものが勝つので、同じコードが本番ではファイルから、コンテナーでは環境変数から、ノート PC では開発者自身のストアから来た値を読みます。アプリケーションのどこにも分岐はありません。

```csharp
// Program.cs — ソースが何かはデプロイの仕事で、コードの仕事ではありません。
builder.Configuration
    .AddJsonFile("appsettings.json", optional: false)
    .AddKeyPerFile("/mnt/secrets", optional: true, reloadOnChange: true)
    .AddEnvironmentVariables();

var connection = builder.Configuration.GetConnectionString("Orders")
    ?? throw new InvalidOperationException("no connection string was injected");
```

`AddKeyPerFile` がマウントされたファイルの経路です。ディレクトリの中のファイル 1 つがキー 1 つで、その中身が値になります。これは Kubernetes のシークレットボリュームや CSI ドライバーが作り出す形そのものです。シーンの 4 番目のステップを成り立たせているのが `reloadOnChange` で、ファイルがその場で置き換わると構成がそれを拾い上げます。ただし、そのマウントがそもそも更新される種類のものである場合に限ります。

ローテーションする値を `IOptionsMonitor<T>` で読めば、現在の値はつねに現在の値になり、アプリケーションは何かがローテーションしたことを知る必要がありません。

```csharp
public sealed class PaymentClient(IOptionsMonitor<PaymentOptions> options)
{
    // 呼び出しごとに読みます。コンストラクターでフィールドに取り込むと、
    // 最初のリクエストがたまたま見た値に凍り付きます。
    private PaymentOptions Current => options.CurrentValue;
}
```

入れ子になったキーが環境変数になるときはアンダースコア 2 つを使います。デプロイが葉 1 つだけを上書きできるようにしてくれる表記なので、覚えておく値打ちのある唯一の文法です。

```yaml
# マニフェストはシークレットの名前を呼びます。値は持ちません。
env:
  - name: ConnectionStrings__Orders
    valueFrom:
      secretKeyRef:
        name: orders-db
        key: connection-string
```

マウントされたファイルは、同じシークレットをもう一方の道で配達したものです。その違いはマニフェストに現れます。ポッドはディレクトリをどこに置きたいかだけを言い、値に関することはどこにも出てきません。

```yaml
volumes:
  - name: orders-secrets
    secret:
      secretName: orders-db
containers:
  - name: api
    volumeMounts:
      - name: orders-secrets
        mountPath: /mnt/secrets
        readOnly: true
```

シークレットがクラスターではなくボールトに住む場合は、構成プロバイダーがワークロード自身の ID を使って起動時に取得します。ですからイメージにも資格情報はなく、マニフェストにもありません。

```csharp
builder.Configuration.AddAzureKeyVault(
    new Uri("https://<vault-name>.vault.azure.net/"),
    new DefaultAzureCredential());
```

ローカル開発では同じキーをリポジトリの外のストアから受け取ります。それが `dotnet user-secrets` のある理由です。暗号化されているわけでも、本番向けの仕組みでもありません。このツールの値打ちは、ファイルが作業ツリーではなくユーザープロファイルに住むということ、つまり誤ってコミットされようがないという一点にあります。

```sh
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Orders" "<local-development-value>"
```

.NET にだけある部品が 1 つ、ディスクではなくストアに置かれるべきです。データ保護のキーリングです。既定ではファイルシステムに書かれるので、コンテナーが再起動するとキーリングを失い、それまでに発行した Cookie とトークンを誰も読めなくなります。永続ストレージを指すようにして、キーそのものはマネージドキーで保護します。

```csharp
builder.Services.AddDataProtection()
    .PersistKeysToAzureBlobStorage(new Uri("<blob-uri-with-no-embedded-key>"), credential)
    .ProtectKeysWithAzureKeyVault(new Uri("<key-identifier>"), credential);
```

目指す形は、シーンが終わる場所そのものです。イメージはどの環境でも同じで、秘密は何も含みません。マニフェストは名前を呼ぶだけで、何も握りません。ストアが値とそのバージョンを所有し、誰が読んでよいかを知り、誰が読んだかを記録します。ローテーションはその 1 か所の変更で、シークレットが配達されてきたその経路をたどって、動いているシステムまで届きます。
