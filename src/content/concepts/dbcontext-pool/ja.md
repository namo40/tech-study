作るのに高いものを借りて使い、返すという規律、それがシーンの 2 番目のステップのすべてで、そこで借りられているのは開いた接続です。`AddDbContextPool` は同じ規律を別のオブジェクト、すなわち `DbContext` のインスタンスそのものに当てます。接続プールを置き換えるのではなくその上に立つ 2 つ目のプールで、まずはっきりさせておきたいのは、2 つのプールが節約している代価が違うということです。接続プールはハンドシェイクと TLS の折衝とログインを節約し、それがシーンの全部です。コンテキストプールはコンテキストのオブジェクトを組み立てる作業を節約し、接続が関わろうと関わるまいとその作業をします。コンテキストが下のプールから接続を借りるのは、実際に何かを実行しているあいだだけだからです。片方を入れてももう片方は変わらないので、コンテキストのプーリングを有効にしてログインが減ることを期待したなら、2 つの層を混ぜてしまっています。

```csharp
builder.Services.AddDbContextPool<OrdersContext>(
    options => options.UseSqlServer(connectionString),
    poolSize: 128);   // 保つのはコンテキストであって接続ではありません
```

節約が実際に何でできているかは控えめなので、当て込むより測るほうが向いています。`DbContext` を 1 つ作るとは、オプションを解決し、内部のサービスプロバイダーを組み、変更追跡器とそれに付く状態を確保するということです。本当に高い成果物であるモデルは、すでにアプリケーションのすべてのコンテキストにわたってキャッシュされており、インスタンスごとに作り直されはしないので、プーリングが避けるのはインスタンスごとの残りです。その残りは絶対量としては小さく、まわりの仕事も小さいときにだけ意味のある割合として現れます。短いクエリ 1 つを回す高スループットのエンドポイント、まさに同じ理由で compiled query が値打ちを持つような経路です。重みのある仕事をするリクエストでは、この組み立ての代価は雑音であり、プールは何も稼がないまま制約だけを載せます。

その制約こそがこの機能の本体です。プールに入ったコンテキストは破棄されるとき壊されません。EF Core がそれを初期化し、変更追跡器を空にし、次の呼び出し元にふさわしい状態へ戻してから、また入れます。初期化が受け持つのは EF 自身の状態で、受け持たないのはあなたが足したものです。だから、プールに入るコンテキストは持ち歩く自分のものを何も持ってはならない、という規則が出てきます。プーリングの対象になるコンテキストの型は、`DbContextOptions` だけを受け取るコンストラクターを持つよう求められますが、この制約は実装上の限界というより、機能が事実を告げている側に近いものです。インスタンスがリクエストより長く生きるのですから、リクエスト単位で注入するものはそもそもありません。フィールドに捕まえたテナント id、生成時に読んだ利用者の身元、`SavingChanges` に結んだイベントの処理、あるリクエストが書き換えた可変のプロパティは次のリクエストまで生き残り、その結果はエラーではなく静かなリクエスト間の状態の漏れです。リクエスト単位の状態が本当に必要なら、`IDbContextFactory` かふつうの `AddDbContext` が正直な答えです。

実務上の点を 2 つ挙げて終わりにします。プールには大きさがあり、それを超えることは失敗ではありません。`poolSize` を超える分はプロバイダーがふつうどおり作り、破棄のときに捨てるので、この設定は同時実行の上限ではなく抱える量の上限です。プールが小さいときの症状は、何かが壊れることではなく、利得が静かになくなることです。そして、この形の全体に EF 固有のものは何もありません。作る値段が初期化する値段より高いオブジェクトなら何にでも object pool が当てる、あの借りと返しであり、採り入れる理由も同じなら気をつける点も同じです。プールに入るオブジェクトは、戻ってくるとき清潔でなければなりません。
