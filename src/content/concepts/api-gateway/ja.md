シーンの最後のステップを見ながら、何が動いていないかに注目してください。席は同じ場所にあり、レーンは同じサービスへ伸び、往復は最初のステップのあの往復です。変わったのは扉の前で投げかける問いの数だけです。この呼び出し元にトークンはあるか、いまもう 1 つリクエストを受ける余地はあるか、このパスはそもそも存在するか、という問いです。違いはこれだけです。API ゲートウェイはリバースプロキシとは別の部品ではなく、ネットワークではなく製品に属する仕事を与えられたリバースプロキシです。

この区別を保つ価値があるのは、2 種類の仕事が違う壊れ方をするからです。TLS を終端し、健康な宛先を選び、パスを書き換え、ヘッダーを転送する判断は、こちらの業務を何も知らなくてもプロキシが正しく下せます。このトークンがこのリソースへの利用を許すのか、この顧客のプランが毎分 60 件を許すのか、モバイルクライアントには応答を削って返すべきなのかは、すべて自分のドメインだけが知る答えです。こうした仕事をエッジへ移すと、製品が変わるたびにエッジをデプロイする必要が出てきます。それこそ、単一の入口が避けようとしていた結合です。

とはいえ、やるなという話ではありません。ある種の関心事は本当に扉の前に属していて、認証がいちばん分かりやすい例です。トークンの署名と有効期限と発行者をエッジで一度検証しておけば、後ろのすべてのサービスは手渡された ID を信じてよく、資格情報のないリクエストはそれに騙されうる何にも届きません。2 つめに分かりやすいのはレート制限です。限度は、すべてのトラフィックが集まる場所にかけて初めて意味を持つからです。サービスごとの限度は、バーストを 3 倍通してしまいます。どちらも、サービスごとに最新に保つライブラリより、前段の規則 1 つにするほうが安上がりで安全です。

野心的で、そして崩れやすいのが組み立てです。魅力は明らかです。クライアントが呼ぶエンドポイントは 1 つ、ゲートウェイが呼ぶサービスは複数、断片から組み上げた応答は 1 つ、だからモバイルクライアントは 5 回ではなく 1 回だけ往復します。厄介なのは、その組み立てコードがいまや触れるすべてのサービスの形を知っている点です。どれか 1 つでフィールド名が変われば誰も予期しなかったデプロイが壊れ、ゲートウェイは、サービスを分けて避けたはずの分散モノリスへとゆっくり育っていきます。よくある規律は、組み立てを浅く読み取り専用に保つことと、本当に違う要求を持つクライアントには共有のゲートウェイに枝を足すのではなく専用の小さなゲートウェイを与えることです。

壊れ方は機能ではなく位置から出てきます。すべてがここを通るので、ここのレイテンシはすべてのリクエストのレイテンシであり、ここの停止は全員の停止です。1 つより多く動かし、設定のリロードを運任せではなく練習済みの作業にしておきます。認可の規則は、それが守るサービスの外に置かれるので、内部アドレスからも届いてしまうサービスは何にも守られていません。シーンでバックエンドに `private` の印が付いている理由であり、その印がほかのどのステップよりこのステップで重い理由です。そしてゲートウェイは本来責任が積み上がる場所なので、どのサービスも試せない場所に規則が積もり続け、ついにはリクエストが受け入れられるか知る方法が 1 つ送ってみることだけになります。

ですからこの呼び名は、下すべき決定ではなく背負った荷物の説明として扱えば十分です。プロジェクトの初めにリバースプロキシと API ゲートウェイのどちらかを選ぶわけではありません。アドレスが 1 つ要るから前に席を置き、そのあと 1 つずつ、次の問いが本当に扉の前に属するのか、それともきちんと答えられるサービスに属するのかを決めていきます。正直に考えて答えが扉の前なら、そこに置いて理由を書き残します。そうでないなら、この席は元のままの席であり続け、それは逃した機会ではなくよい結果です。
