## いつ使うか

- 公開されている HTTP の面であればどこでも、アプリケーションに触れずに得られる追加の層として使います。管理された形は、すでに経路に置かれている何かに付けるポリシーです。Azure Front Door の WAF ポリシーや Application Gateway の WAF ポリシーがそれにあたります。ですから決めるのは何を入れるかではなく、トラフィックがすでにどこで終端しているかです。付けてもコードは変わらず、コードが負う義務も減りません。この事実が、価値と限界を同時に読むための正しい読み方です。
- 広く知られた攻撃の形に合うトラフィックをふるい落とすために使います。OWASP Core Rule Set のようなルールセットには、ありふれた攻撃に現れるパターンが入っています。スキャナーが送るペイロード、自動化されたインジェクションの試みに出てくる文字列、パストラバーサルの形などです。公開されたエンドポイントに届くものの多くはこちらを名指しで狙った攻撃ではなく、一般的な攻撃には一般的なルールセットがよい答えになります。
- 脆弱性が公になった時点とデプロイの間の時間を稼ぐために使います。依存先に脆弱性が見つかり、直ったバージョンまで数日あるなら、脆弱な経路に届くリクエストを拒む狭いルールは、数分で入れられて本当の修正が出たら外せる緩和策です。いつ外すのかをルールの説明にも書いておきます。誰も外さない一時的なルールは、説明のない振る舞いとして残り続けます。
- 見えるようにするために使います。どのルールに何が当たり、どのアドレスから来て、どのルートに向かっていたのかが残るログは、こちらに対して何が試されているかの記録であり、実際に何かを止めたかどうかとは関係なく貯まります。その記録は、チームが自分の攻撃面を初めて正直に眺める絵であることが多く、何も拒まない設定のままでも持つ価値があります。

## 注意点

- 前に立てる層であって、内側の防御の代わりではありません。クエリを安全にするのは値のパラメーター化です。値が、パーサーがコードとして読まない通り道を進むからです。値を画面に書くときに安全にするのは文脈に合った出力のエンコードで、システムがそもそも受け付ける値の範囲を狭めるのが入力の検証です。手前にフィルターが 1 つ立ったからといって、このどれも省略できるようにはなりません。ルールセットは教わったパターンを見分けるだけで、その見分けに安全を預けるアプリケーションは、他人の書いた正規表現に自分の安全を決めさせているアプリケーションです。
- 誤検知の調整が運用の大半で、そこを飛ばすと WAF は結局切られます。本物のユーザーも攻撃に見える文章を送ります。SQL について書かれた書き込み、記号の混ざったパスワード、マークアップだらけの文書の投稿などです。初日から遮断の設定にしたルールセットは、そのいくつかを拒みます。まず検知だけの設定で始め、実際のトラフィックと突き合わせて定期的に走る処理まで一巡り見届けてから、できるだけ狭い例外とともに遮断へ移します。このルール、このパラメーター、このルート、というところまで絞ります。
- 迂回は存在し、信頼の境界はいまもアプリケーションです。フィルターは自分が解釈したリクエストについて判断するので、その解釈とアプリケーションの解釈の差がそのまま隙間になります。ルールセット自体も、変わり続ける攻撃を相手に手入れされ続ける動く的です。通り抜けたリクエストはフィルターがなかったときとまったく同じに信頼しない値として扱い、遮断されたリクエストは脆弱性が閉じたのではなく雑音が減ったのだと読みます。
- 検査には平文が要るので、WAF は TLS が終端する場所に置かれます。そこは layer 7 の負荷分散やリバースプロキシの層と同じ地点であり、その層から先の接続はこちらが別に守る 2 つ目の区間だという意味でもあります。また、フィルターが読めるものはその層が記録できるものでもあるので、ログに何を残してよいかの決まりはそこにも同じように掛かります。

## .NET では

- アプリケーションに入れるものはありません。これはアプリケーションに足すパッケージではなくアプリケーションの隣に置くプラットフォーム層の制御で、そのおかげでデプロイなしに変更でき、締められ、戻せます。その代わりインフラを持つ設定の仕組みの中にあるので、コードベースではなくインフラと同じレビューに乗せます。
- ルールセットのバージョンはデプロイの判断として扱います。管理されたルールセットには新しいバージョンが出て、新しいバージョンはどのリクエストが拒まれるかを変えます。アプリケーションの外側にある何かが、アプリケーションから見える変更を起こすということです。バージョンを固定し、上げるときは意図をもって上げ、最初に入れたときに通した検知だけの観察を、更新のときにも同じように通します。
- 遮断されたリクエストはアプリケーションに届かないので、アプリケーションのログには決して現れません。この非対称さが障害対応で人を捕まえます。ユーザーは失敗を訴えているのに trace には何もなく、答えは 1 つ上の層にあります。WAF のプラットフォーム診断ログをアプリケーションのテレメトリーと同じ置き場へ送り、プラットフォームがログとエラーページの両方に残す追跡用の識別子で結び付けておけば、1 回のクエリで境界の両側を見られます。
- トラフィックがプロキシを経て届くようになったので、こちらから教えないかぎりアプリケーションはプロキシのアドレスを見ます。転送ヘッダーを設定して本来のクライアントのアドレスとスキームが映るようにします。`UseForwardedHeaders` を使い、`ForwardedHeadersOptions.KnownProxies` か `KnownNetworks` を、何でも信じる設定のままにせず WAF 層のアドレスに絞ってください。転送ヘッダーを自分で決められるリクエストは、その上に積んだもの、つまりクライアントごとのレート制限や監査の記録や地域によるルールにおける自分の ID も、自分で決められてしまうからです。
