## いつ使うか

- 公開されている HTTP の面であればどこでも、アプリケーションに触れずに得られる追加の層として使います。管理された形は、すでに経路に置かれている何かに付けるポリシーです。Azure Front Door の WAF ポリシーや Application Gateway の WAF ポリシーがそれにあたります。ですから決めるのは何を入れるかではなく、トラフィックがすでにどこで終わっているかです。付けてもコードは変わらず、コードが負う義務も減りません。この事実が、価値と限界を同時に読むための正しい読み方です。
- 広く知られた攻撃の型に合うトラフィックを濾し取るために使います。OWASP Core Rule Set のような規則の集合には、ありふれた攻撃に現れる型が入っています。スキャナーが送るペイロード、自動化された注入の試みに出てくる文字列、経路をたどる攻撃の形などです。公開された端点に届くものの多くはこちらを名指しで狙った攻撃ではなく、一般的な攻撃には一般的な規則の集合がよい答えになります。
- 脆弱性が公になった時点と配備の間の時間を稼ぐために使います。依存に脆弱性が見つかり、直った版まで数日あるなら、脆弱な経路に届く要求を拒む狭い規則は、数分で入れられて本当の修正が出たら外せる緩和策です。いつ外すのかを規則の説明にも書いておきます。誰も外さない一時的な規則は、説明のない振る舞いとして残り続けます。
- 見えるようにするために使います。どの規則に何が当たり、どの住所から来て、どの経路に向かっていたのかが残る記録は、こちらに対して何が試されているかの記録であり、実際に何かを止めたかどうかとは関係なく貯まります。その記録は、チームが自分の攻撃面を初めて正直に眺める絵であることが多く、何も拒まない設定のままでも持つ価値があります。

## 注意点

- 前に立てる層であって、内側の防御の代わりではありません。問い合わせを安全にするのは値のパラメーター化です。値が、構文解析器がコードとして読まない通り道を進むからです。値を画面に書くときに安全にするのは文脈に合った出力の符号化で、システムがそもそも受け付ける値の範囲を狭めるのが入力の検証です。手前に濾し器が 1 つ立ったからといって、このどれもが選択肢になったりはしません。規則の集合は教わった型を見分けるだけで、その見分けに安全を預けるアプリケーションは、他人の書いた正規表現に自分の安全を決めさせているアプリケーションです。
- 誤検知の調整が運用の大半で、そこを飛ばすと WAF は結局切られます。本物の利用者も攻撃に見える文章を送ります。SQL について書かれた書き込み、記号の混ざったパスワード、マークアップだらけの文書の投稿などです。初日から遮断の設定にした規則の集合は、そのいくつかを拒みます。まず検知だけの設定で始め、実際のトラフィックと突き合わせて定期的に走る処理まで一巡り見届けてから、できるだけ狭い例外とともに遮断へ移します。この規則、この引数、この経路、というところまで絞ります。
- 迂回は存在し、信頼の境界はいまもアプリケーションです。濾し器は自分が解釈した要求について判断するので、その解釈とアプリケーションの解釈の差がそのまま隙間になります。規則の集合自体も、変わり続ける攻撃を相手に手入れされ続ける動く的です。通り抜けた要求は濾し器がなかったときとまったく同じに信頼しない値として扱い、遮断された要求は脆弱性が閉じたのではなく雑音が減ったのだと読みます。
- 検査には平文が要るので、WAF は TLS が終わる場所に住みます。そこは layer 7 の負荷分散やリバースプロキシの層と同じ地点であり、その層から先の接続はこちらが別に守る 2 つ目の区間だという意味でもあります。また、濾し器が読めるものはその層が記録できるものでもあるので、ログに何を残してよいかの決まりはそこにも同じように掛かります。

## .NET では

- アプリケーションに入れるものはありません。これはアプリケーションに足す部品ではなくアプリケーションの隣に置くプラットフォーム層の制御で、そのおかげで配備なしに変更でき、締められ、戻せます。その代わりインフラを持つ設定の仕組みの中に住むので、コードベースではなくインフラと同じ確認の流れに乗せます。
- 規則の集合の版は配備の判断として扱います。管理された規則の集合には新しい版が出て、新しい版はどの要求が拒まれるかを変えます。アプリケーションの外側にある何かが、アプリケーションから見える変更を起こすということです。版を固定し、上げるときは意図をもって上げ、最初に入れたときに通した検知だけの観察を、更新のときにも同じように通します。
- 遮断された要求はアプリケーションに届かないので、アプリケーションのログには決して現れません。この非対称さが障害対応で人を捕まえます。利用者は失敗を訴えているのに追跡には何もなく、答えは 1 つ上の層にあります。WAF のプラットフォーム診断ログをアプリケーションのテレメトリと同じ置き場へ送り、プラットフォームがログと画面の両方に残す追跡用の識別子で結び付けておけば、1 回の問い合わせで境界の両側を見られます。
- トラフィックがプロキシを経て届くようになったので、こちらから教えないかぎりアプリケーションはプロキシの住所を見ます。転送ヘッダーを設定して本来の利用者の住所と方式が映るようにし、そのとき何でも信じるのではなく、既知のプロキシとネットワークを指定して設定してください。転送ヘッダーを自分で決められる要求は、その上に積んだもの、つまり利用者ごとの流量制限や監査の記録や地域による規則における自分の身元も、自分で決められてしまうからです。
