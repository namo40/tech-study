## いつ使うか

エラーバジェットは、オンにする監視機能ではありません。100% 未満の信頼性目標を書き留めた瞬間に無料で付いてくるものであり、残る問いは、それを誰かが意図して使っているかどうかだけです。

- 「これ、出していいですか」が役職で決まっているなら、持ち出すときです。この議論は自然には終わりません。抽象的にはどちらも正しいからです。リリースは製品が生き延びる方法であり、安定はお客さんが残る方法です。予算は答えを引き算に変えて議論を終わらせます。8% しか残っていないのは十分ではないと、誰かを説得する必要はありません。
- チームの外からも見える SLO ができたら、すぐ導入します。予算の付いていない目標は願い事です。外しても何も変わらず、大きく上回っても何も変わらないからです。予算はその数字をてこに変えます。しかも両方向にです。慎重になりすぎているときにも教えてくれます。
- リスクを禁じる道具ではなく、値段を付ける道具として使います。70% 残っている予算は許可です。業務時間に移行を走らせてよい、カナリアを 50% まで上げてよい、三つ目の承認は飛ばしてよい、という許可です。予算を一度も使わないチームは安全なのではなく遅いのであって、使われなかった分がその証拠です。
- 障害をひとつずつ切り離して言い争っているときに持ち出します。二時間の停止は、その月がすでに何を使ったかによって、大惨事にも丸め誤差にもなります。それを判断できるのは予算だけです。予算は個別の騒ぎの連続を、全員が同じように読むひとつの累計に変えます。
- 実際に配線したリリースゲートと組み合わせます。予算は何かが読むまでは数字にすぎません。パイプラインの検査、変更承認のルール、何を凍結するかについての常設の合意が読む必要があります。シーンの三番目の段階がまさにその話で、ゲートが勧告ではなく結果だから機能します。
- 人を評価する指標には使わないでください。燃やした予算が誰かの責任を問われる対象になった瞬間、SLI はよく見えるように定義され始めます。そうなれば、意思決定の道具を報告の道具にすり替えたことになります。予算が測るのはシステムであり、予算の存在理由は使われることです。

## 注意点

- SLI は利用者が実際に感じるものを測らなければなりません。自分のサーバーログから計算した成功率では、そもそも届かなかったリクエスト、DNS の失敗、コードが動く前にロードバランサーが返した 503、9 秒かかった 200 のどれも見えません。イングレスや CDN、クライアントといった端で測るか、あるいは自分の予算が「動いていた部分」の指標にすぎないことを受け入れるかです。
- 100% の SLO は予算がゼロということであり、恒久的な凍結ということです。野心のように聞こえますが、ただの算数です。何も失敗してはいけないなら、すべてのデプロイが違反であり、正直な対応はデプロイをやめることです。誰かが「無停止」を求めたときに役立つ問いは、100% の下のどの数字のことかです。必ずひとつを念頭に置いているからです。
- バーンレートのアラートは窓が最低ふたつ必要で、そうでなければノイズで鳴ります。短い窓ひとつではあらゆるさざ波を拾い、長い窓ひとつでは障害が終わってから気づきます。標準的な形は速い組と遅い組です。速い組は一時間あたりの高い倍率を 5 分で確認して人を起こし、遅い組は一日あたりの低い倍率を数時間で確認してチケットを残します。窓がひとつだけのアラートは、一週間で誰にも信じられないポケベルになります。
- 毎回上書きされる凍結は、ポリシーではなくダッシュボードです。予算に決定を下させるには、ゲートより上の立場の人たちが前もってそれに従うと合意している必要があり、その合意は予算が満杯で何も燃えていないうちに済ませておくものです。誰が上書きしてよいのか、その代償は何かを書き留めてください。例外の手続きは構いませんが、何も言われないまま定着した習慣は困ります。
- 期間が変わると予算は満たされますが、説明は何も残りません。4% 残して終わった月と、まったく別の理由で 4% 残して終わった月は、翌月の 1 日には同じに見え、リセットは両方を静かに埋めてしまいます。大事なのはリセット直前の振り返りです。何が予算を使ったのか、目標は正しかったのか、そしてシステムと約束のどちらを変えるべきなのかを見ます。
- 燃える速さだけでなく、予算の大きさも見ます。30 日で 99.9% は 43 分ですが、一日なら 86 秒です。月単位の数字を約束しておいて週単位で考えるチームはよくありますが、それは余裕が 4 分の 1 の同じ約束です。目標を口にするたびに期間も一緒に言ってください。ふたつそろって予算であり、片方だけでは予算ではありません。
- ひとつの体験にひとつの予算を置きます。すべてのエンドポイントをひとまとめにした可用性の数字は、健全な決済に壊れた検索を隠させ、人が来た目的の機能が動かないのに合計は緑のままになります。重要な利用者の体験をいくつか選び、それぞれに SLI を与え、サービスによっては予算がひとつではなく三つ要ることを受け入れます。

## .NET では

- すでに出しているテレメトリーから SLI を計算します。ASP.NET Core に組み込みの `http.server.request.duration` メトリックは状態コードとルートをタグとして持っているので、成功率は新しいパイプラインではなくひとつのカウンターに対する比です。「良い」の定義は一度だけ決めます。おかしなリクエストを送ったクライアントはサービスの失敗ではないので 4xx は除き、その定義を SLO の隣に置いておきます。

```csharp
// The SLI: the share of served requests that were good, by route.
// 5xx is the service failing; 4xx is the caller, and does not spend budget.
builder.Services.AddOpenTelemetry().WithMetrics(metrics => metrics
    .AddAspNetCoreInstrumentation()
    .AddPrometheusExporter());
```

- 目標と期間はクエリではなく設定に置きます。予算は決められた期間に対する `1 - SLO` であり、すべてのアラート閾値はその倍数なので、目標を一箇所に書いておけば約束が変わったときにアラートも一緒に動きます。

```csharp
public sealed record ReliabilityTarget(double Slo, TimeSpan Window)
{
    // 99.9% over 30 days is 43.2 minutes of failure, funded in advance.
    public TimeSpan Budget => Window * (1 - Slo);

    // A burn rate of 1 spends exactly the budget over exactly the window.
    public double BurnRate(double goodRatio) => (1 - goodRatio) / (1 - Slo);
}
```

- アラートは窓ひとつではなくふたつで組みます。Azure Monitor では、評価の頻度が短く集計の粒度が長いメトリックアラートのルールが長い窓になり、どちらも短い二番目のルールが確認用の窓になります。この組は遅い信号と速い信号が一致したときだけ鳴ります。速いルールは一時間でバーンレート 14 倍、遅いルールは六時間で 6 倍あたりを目安にし、誰かの携帯電話をつなぐ前に本物のトラフィック一か月分で倍率を調整します。
- 予算は人ではなくパイプラインに読ませます。Azure Pipelines のゲートでも、GitHub Actions のジョブでも、デプロイリングの検査でも、メトリックを問い合わせてステージを失敗させられますし、そうして初めて凍結が本物になります。検査は軽くしておき、失敗のメッセージは具体的に書きます。数字と期間、そして越えた閾値を一緒に載せます。

```csharp
// A release gate: the deployment stage fails when the budget is spent.
var remaining = 1 - spentMinutes / target.Budget.TotalMinutes;
if (remaining < 0.10)
{
    Console.Error.WriteLine(
        $"error budget {remaining:P0} remaining over {target.Window.TotalDays:N0} days; releases are frozen");
    return 1;
}
```

- 可用性テストは、誰も呼ばないエンドポイントの SLI を作ってくれます。Application Insights の標準テストは複数のリージョンから定期的に走り、成功したかどうかと所要時間を記録します。これはまさにクライアントが行う測定であり、サーバー側のメトリックでは作れない値です。サービスが単に不機嫌なのか、そもそも届かないのかに気づく、いちばん安い方法です。
- ヘルスチェックは SLI ではありません。`AddHealthChecks` が答えるのは「このインスタンスはトラフィックを受け取ってよいか」であり、ひとつのプロセスのひとつの瞬間についての問いです。予算はひと月のあいだに利用者が何を受け取ったかについての問いです。どちらも用意したうえで別々に保ち、レディネスの結果から可用性を計算しないでください。正しくローテーションから外されたインスタンスは、誰も失敗させていません。
