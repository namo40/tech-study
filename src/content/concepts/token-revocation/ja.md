シーンの 4 番目のステップは、前の 3 つには必要のなかったゲートを 1 つ足します。それが最初からそこにあるのではなく、あとから足されなければならないという事実こそが、この話題のすべてです。ほかのゲートはトークンを読みます。署名は鍵と、有効期限は時計と、audience は設定に書かれた文字列と突き合わされます。どれも誰にも何も尋ねません。取り消しの確認はそのようには働けません。「このトークンは回収された」はトークンが運んでいる事実ではありませんし、これからもそうはなりません。それはトークンがすでに世に出たあとで誰かが記録した事実であり、API がそれを知る唯一の方法は、見に行くことです。

ですから取り消しは照会であり、照会こそ自己完結のトークンを採り入れて避けようとしたコストです。こう置いてみると設計が正直になります。問いは取り消しを持つかどうかではなく、どの呼び出しがそのコストを払うかであって、よくある答えはこうです。アクセストークンには誰も回収する必要がないほど短い寿命を与え、何日も生きるリフレッシュトークンを設計として回収可能にします。リフレッシュトークンを殺せば、アクセストークンの寿命 1 つ分のうちにセッションは終わります。ホットパスに照会を 1 つも足さずにです。

拒否リストが本当に必要なときは、構造として小さく保ってください。リストには回収済みでまだ満了していないトークンだけが入ればよいので、項目ごとに死ぬ時刻が自然に決まります。だから保存先は誰かが掃除するテーブルではなく、TTL の付いたキャッシュで足ります。キーはトークン自身の id、つまり `jti` クレームです。いつか回収するかもしれないトークンに `jti` が要る理由がそれです。トークン全体をハッシュしても働きますが、長いうえに、リストを眺めてこれが何だったかと考えるとき何も教えてくれません。リストを API のインスタンスごとに読み込み、短い間隔で更新すれば、確認のコストはネットワーク呼び出しではなくハッシュ集合の参照になります。かわりに伝播の遅れが生まれ、その遅れは秒で言えるようにしておくべきです。

もう 1 つの形は introspection です。API がローカル検証をやめ、受け取ったトークンごとに認可サーバーに尋ねる方式です。即座で正確な答えが得られるかわりに、ローカルの確認が買っていたものをすべて手放します。issuer がすべてのリクエストの経路に乗り、issuer の可用性がこちらの可用性になり、issuer のレイテンシがこちらのレイテンシに足されます。不透明なトークンや、呼び出し量が少なく機微の高い API には向きます。一般の場合には向きませんし、取り消しが雑に見えるという理由でこちらへ手を伸ばすのが、状態を持たない設計が静かに状態を持ってしまう道筋です。

ローテーションはもう半分で、正直なクライアントが実際に経験する部分です。トークンが回収されるとき、クライアントは罰せられているのではなく、新しいものを取りに来るよう求められているのであって、すでに定期的に更新していたクライアントは何にも気づきません。リフレッシュトークンのローテーションは、これを整っているだけの話から役に立つ話に変えます。更新のたびに新しいリフレッシュトークンが返り、古いものは退くので、同じリフレッシュトークンが 2 度目に提示されたなら、どこかに複製があるという証拠です。そのときの正しい対応は、その系列をまるごと取り消し、本物のユーザーにもう一度サインインしてもらうことです。盗難が、防げるよう祈る対象から、検知できる対象に変わります。

残るのは運用の分で、必要になる前に決めておくのがよいところです。侵害のときに何を回収する必要があるかを知っておいてください。セッション 1 つか、ユーザー 1 人のすべてのセッションか、クライアント 1 つが発行したすべてのトークンかです。伝播の遅れがどれくらいかを知っておいてください。事故のさなかに聞かれる数字がそれです。そして拒否リストが、大事な経路では確認され、そうでない経路では飛ばされていることを確かめてください。誰も引かない取り消しは、何の効果もないデータベースの行にすぎません。
