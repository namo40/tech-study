シーンの最初の段階で A は 1 番のインスタンスにログインし、次のリクエストは 2 番に落ち、2 番は A を見たことがありません。セッション状態とは、まさにその 2 番に欠けているものです。HTTP 自体は何も覚えないので、リクエストとリクエストのあいだにサーバーが持ち続けるユーザーごとのデータが要ります。行き来するのはクッキーに入った意味のないセッション id だけで、発行したサーバーの外では意味を持たない無作為の文字列です。中身はサーバー側に残ります。セッション状態と、クッキーそのものに入れたデータとを分ける線がここです。クッキーに入れた値はリクエストのたびに運ばれ、形が見え、数キロバイトに縛られます。セッションに入れた値は id で引き当て、保管庫が許すだけ大きくなれます。

その中身をどこに置くかがアーキテクチャを決め、しかもかなり早い段階で決めてしまいます。プロセスのヒープの辞書に持てば、id はそれを発行した 1 台の中でしか意味を持たないので、ロードバランサーはそのユーザーを同じ台へ送り続けるほかありません。sticky session が存在する理由はすべてここにあり、sticky session の居心地の悪さもすべてこの選択ひとつから出てきます。負荷はリクエスト単位ではなくセッション単位で分かれ、再起動は状態ごと持ち去り、台数を減らせば人がログアウトします。同じ中身をすべてのインスタンスが届く保管庫へ移せば、id はどこでも意味を持ち、インスタンスは互いに取り替えが利くようになり、sticky session は必須ではなく任意の最適化に下がります。外部の保管庫そのものの話は distributed session の担当です。ここで大事なのは、ライブラリの選択ではなく置き場所の選択が配置の形を決める、という点です。

ユーザーごとの値なら何でもセッションに入れてよいわけではありません。セッションが似合うのは、作り直せないのにまだデータベースの行をもらう資格のないものです。書きかけのフォーム、ウィザードの 3 番目の段階、決済前のかごといったものです。データベースから計算し直せる値は、ユーザーごとのキーを付けたキャッシュに置くほうがよく、保管庫を失っても残らなければならない値はデータベースにあるべきです。セッションのエントリはそもそも最善努力なので、この区別が効いてきます。期限が来れば消え、メモリが足りなければ追い出され、保管庫が再起動すれば失われます。前のリクエストで書いたものが今回もあると考えず、読むたびに無い場合を扱ってください。身元は別の話で、別にしておくほうが安全です。利用者が誰かは認証クッキーか bearer token が運ぶので、セッションを失って払う代償はかごであって、ログインであってはなりません。

したがって現場の規律は、小さく、そして少なく持つことです。セッションに入れた値は、それに触れるリクエストのたびに代金を払います。状態をプロセスの外へ移したあとは、シリアライズと往復がその代金です。セッションがいつのまにか何でも入れる引き出しに育っていることが、外部化を高く感じさせるよくある理由です。2 台目が現れたあとではなく、現れる前に置き場所を決めてください。あとから直す作業が、シーンの 3 番目の段階に出てくる障害になります。中身は、外へ移す作業が設定変更で済むくらい小さく保ち、失うと痛む値はそもそもセッションに置くものではなかったと考えれば足ります。
