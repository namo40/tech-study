シーンの 2 番目のステップは、多くの人がこの言葉を聞いて思い浮かべる切り方です。スキーマは変わりません。どのパートも同じ列、同じインデックス、同じ形を持ち、パートどうしの唯一の違いはどの行を持っているかです。シーンで 2 枚のカードが同じ 3 本のバンドを描くのはそのためです。どのパートを見ても、自分が持たない行がどこか別の場所にあるということ以外に、それがパートだと教えてくれるものはありません。

そうして買ってくるのが容量で、行数につれて増えるすべての軸で一度に買ってきます。書き込みが分かれるので、1 台の機械が全部を受けることはありません。ロックはテーブル全体ではなくパートの中で競合するので、あるパートの長いトランザクションはほかのパートからは見えません。キャッシュは全体の端数ではなく、1 つのパートの意味のある割合を保持します。バックアップは終えられる 1 切れだけを覆い、復元は残りが提供を続けているあいだに 1 つのパートだけを戻し、インデックス再構築は 1 か月前に予定を組む仕事ではなくなります。どれも人がこの手を取る表向きの理由ではありませんが、合わせるとたいていそれが本当の理由です。

キーが決定のすべてです。キーは速くあるべきすべてのクエリに入っていなければなりません。キーのないクエリは 1 つのパートへ送れず、全部を訪ねることになるからです。キーは行を均等に散らさなければなりません。寄せてしまうキーは、ほかが遊んでいるあいだに 1 つのパートへシステムを背負わせるからです。そしてキーは変わってはいけません。行のありかを決める値を直すことはストアのあいだで行を動かすことであり、その行が 2 か所にあるか、どこにもないあいだ、読む側に何を保証するのかまで決めなければならないからです。テナント id、ユーザー id、アカウント id のように、一度割り当てられてずっと参照されるものが向いています。

範囲のキーとハッシュのキーは違う壊れ方をするので、その違いは選ぶ前に知っておく値打ちがあります。キーに範囲を取れば隣り合うものが一緒にいるので、「この顧客の 3 月から 6 月まで全部」が fan-out ではなく 1 つのパートの中のスキャンになります。ところが時刻に範囲を取ると、新しい行は全部いちばん新しいパートへ行きます。シーンの 4 番目のステップがまさにそれです。紙の上では完璧に釣り合って見えて、動き出した途端に 1 つのパートがすべての書き込みを受けます。ハッシュは仕組みとして均等に散らす代わりに、範囲スキャンを丸ごと諦めます。隣り合うキーが互いの近くには落ちないからです。複合キーは両方を少しずつ買ってきますが、頭に収めにくい規則を対価に払います。

手放すのは、かつて無料だった保証です。トランザクションはパートをまたげないので、2 つのパートに触れる操作には saga か outbox が要るか、2 つの半身が別々に落ち着くことを受け入れる必要があります。一意インデックスもパートをまたげないので、キー以外の一意性はアプリケーションか別のストアの問題になります。パートをまたぐ外部キーはそもそも強制できません。違うキーで分けられたテーブルどうしの結合は結合であることをやめ、2 本のクエリと少しのコードになります。どれにも使える答えはあります。要点は、以前は無料で、いまはそうではないということです。

パートの数は一度決めるのは簡単で後から変えるのは難しい決定なので、意識して決める値打ちがあります。キーのハッシュをパート数で割った余りは誰もが最初に書き下ろす規則で、同時に数が変わればほとんどすべての行を動かすことになる規則でもあります。consistent hashing がある理由がこれです。キーの範囲とデータベースを対にして保存する shard map は、照会 1 回を費用に払って、ほかのパートに触れずに 1 つのパートを 2 つに割る力を買ってきます。どちらもデータを動かす費用をなくしはしません。どれだけのデータが動くのかを変えるだけです。

システムの運用の大きさはパート数につれて増え、その増え方は人が数え忘れるところで線形に効きます。パートのひとつひとつが接続プールであり、監視の対象であり、バックアップの予定であり、パッチの窓であり、フェイルオーバーの計画であり、移行が途中で失敗しうる場所です。2 つのパートは 1 つよりほんの少し手間が増えるだけです。16 のパートは別の仕事です。計算がきれいに割り切れる数ではなく、いちばんひどい 1 週間でも回せる数を選んでください。

.NET にはこのためのフレームワーク機能はありません。フレームワークにはそのキーが分からないからです。代わりにあるのは、キーから接続文字列への小さなマップと、そのマップが返した接続に対して作る `DbContext` と、キーのないクエリを偶然データベースに届かせない規律です。Azure SQL Database は同じ考えを shard map manager を備えた elastic database tools としてまとめており、Cosmos DB はパーティションキーをコンテナー定義の一部にして、その選択が一度宣言され、静かに流れていかないようにしています。
