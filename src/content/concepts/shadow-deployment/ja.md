## いつ使うか

- 変更が大きすぎて、ステージングでは動くかどうか分からないときに持ち出します。新しいストレージエンジン、フレームワークの移植、書き直した価格ルールのように挙動が同じであるべき変更は、古い版が受け取っているまさにその入力を相手に走らせるのが唯一正直な確かめ方です。シャドウデプロイはもう 1 つの試験環境ではなく、実際の入力をサービスの 2 つ目の写しに向け、その応答を比べる作業です。
- 問いが正しさではなく容量のときに使います。「v2 は本番の量に耐えるか」という問いの量は、信頼できる出所が 1 つしかありません。ミラーリングされた流れは、生成器が想像した分布ではなく、実際の到着パターン、実際のキー分布、実際のペイロードの大きさを与えてくれます。ただし負荷試験や容量試験の代わりにはなりません。そちらは今日のトラフィックの先へ意図的に押し込む手段で、シャドウは今起きていることしか見せません。2 つを併用し、合成モデルが間違っていたという事実はシャドウに言わせるのがよいでしょう。
- フラグを切り替える前に長く寝かせる検証に使います。カナリアは新しいコードを実ユーザーの一部に見せますが、シャドウは誰にも見せません。だからカナリアの競合ではなくその前の段階であり、重大なバグの代償が謝罪ではなくレポートの不一致 1 行で済む唯一の段階です。何日か何週間か回したあとの昇格は退屈です。その版はすでにその仕事をしてきたのですから。
- 読み取りの多いサービスから始めます。檻を作る費用がいちばん安いからです。検索エンドポイント、価格計算、推薦の呼び出しは、抑えるものがほとんどないまま本物の経路を回せます。書き、請求し、通知する仕事が多いサービスほど、最初の写しを送る前に必要な設定が増え、下に書いた棚卸しもそれだけ丁寧でなければなりません。
- 挙動を仕様に書くのは難しいのに、比べるのは易しい場面でいちばん報われます。答えがどうあるべきか書けなくても、現行版が言うものと同じであるべきだとは言えます。比較器はその一文を、数百万件の実リクエストの上で測れる性質に変えてくれます。

## 注意点

- 副作用が危険のすべてであり、棚卸しは最初のミラーリングされたリクエストの後ではなく前に来ます。サービスを前にして、外へ出すものをすべて書き出します。書き込まれる行、取られる決済、出ていくメールとプッシュ、発火するウェブフック、発行されるメッセージ、呼ばれる下流サービス。そのひとつひとつについて、抑えるのか、モックに替えるのか、代役に向けるのかを決めます。その一覧が閉じてから初めてミラーリングを入れます。順序を逆にすると、サービスが何を出すのかを、二度出ていく光景を見ながら知ることになります。
- 檻を作るのは設定であって分岐ではありません。シャドウは昇格するつもりのその成果物でなければなりません。そうでなければ、これから動くことのないビルドについて何かを証明したことになります。フィーチャーフラグは切り、メール送信は何もしない実装に差し替え、接続文字列は読み取りレプリカへ、決済ゲートウェイはサンドボックスへ向けます。すべて起動時に適用される設定から来るので、昇格するものは試験したものとまったく同じです。
- 2 倍になった負荷は本物で、誰かがその代金を払います。ミラーリングは共有する依存先ごとに読み取りトラフィックを 2 倍にするので、データベースもキャッシュもすべての下流サービスも 2 倍を捌くことになります。その分の容量を用意するか、シャドウにレプリカや自前のキャッシュのような別のデータ経路を与えるかです。後者を選ぶと 2 つの版が少しずつ違うデータを読むことになり、それ自体が不一致の原因になります。
- 比較には正規化が要ります。さもないと不一致が雑音に沈みます。タイムスタンプ、生成された id、リクエストごとのカウンター、マップの走査順、浮動小数点の表記はリクエストのたびに違い、それらをすべて報告する比較器は何も報告していないのと同じです。変わって当然のフィールドを正規化し、バイトではなく構造で比べ、雑音の予算を設計の一部として扱います。ゼロの近くまで下げられない不一致率は、コードの問題ではなく比較器の問題です。
- ミラーリングされたトラフィックは、誰にも応答しないコード経路へ実ユーザーのデータを運びます。応答しないからといってデータが本物でなくなるわけではありません。シャドウは本番と同じ個人データ、同じトークン、同じリクエスト本文を見ます。ですからアクセス制御も、ログの伏せ字も、保持ルールも、データマップ上の位置も本番と同じであるべきです。アクセスとプライバシーの観点では本番として扱ってください。実際にそうだからです。
- 全量のミラーリングがいつも見合うとは限りません。ふつうは標本を取ります。固定の割合か、一部のテナント全体を使うやり方で、本番トラフィックの 10% でも生成器とは比べものにならないほど代表性があります。ただし意図を持って取るのがよいでしょう。均一な標本は珍しいリクエストの形を取りこぼしますが、シャドウがいちばんうまく捕まえるバグは、まさにそういう入力から出てきます。
- シャドウが触ってよい対象は、二度触っても平気なものでなければなりません。同じリクエストを 2 つの版が処理するようになったので、共有するキューのコンシューマー、カウンター、両方が書く idempotency key（重複防止のキー）は、重複事故が起きるのを待っている場所です。これは idempotent consumer（同じメッセージを繰り返し受け取っても結果が変わらないコンシューマー）の規律を 2 人目の読み手にも当てはめる話であり、「書かせておいて後で片づける」より「代役に向ける」のほうが安全な助言である理由でもあります。
- シャドウは応答が一致することを証明するだけで、新しい版が良いことを証明しません。古い挙動が正しかったかは教えてくれず、まだ誰も送っていないリクエストについては何も見えず、2 つの版が同じように間違っているという事実も喜んで確認してくれます。品質のきわめて高い回帰の網であって、それ以上ではありません。

## .NET では

端ではミラーリングはたいていメッシュの仕事です。Istio と Envoy はある経路のトラフィックの写しを 2 つ目の宛先へ送り、その応答を捨てるので、アプリケーションは分岐を見ません。

```yaml
# 写しは投げっぱなしです。呼び出し元は live が応答し shadow を待たないので、
# 遅いシャドウや失敗するシャドウがユーザーの問題になることはありません。
http:
  - route:
      - destination: { host: checkout, subset: live }
    mirror: { host: checkout, subset: shadow }
    mirrorPercentage: { value: 10.0 }
```

メッシュがなければ、プロキシの前に置く小さなミドルウェア（YARP でもそれ以外でも）でリクエストを複製できます。YARP 自体に有効にできるミラーリング機能はありません。写しはバッファに取られてから別に送られるので、ユーザーの応答がそれで足止めされることはありません。

```csharp
app.Use(async (context, next) =>
{
    context.Request.EnableBuffering();
    var copy = await ShadowRequest.CaptureAsync(context.Request);
    context.Request.Body.Position = 0;

    // ユーザーの呼び出しはすぐに先へ進みます。写しはシャドウへ発射され、
    // その応答は比較器へ行き、この応答へ戻ってくることはありません。
    // `ShadowRequest` と `shadow` は自分で書くものです。この行より後では、その中の
    // 何も `context` に触れてはいけません。リクエストはもう終わっているかもしれない
    // からです。このタスクは誰も await しないので、失敗は自分でログに残します。
    _ = shadow.SendAndCompareAsync(copy, context.TraceIdentifier);
    await next(context);
});
```

檻そのものはありふれた設定です。環境が与える値を起動時に一度読みます。

```csharp
var role = builder.Configuration["Deployment:Role"];   // "live" または "shadow"
var caged = role == "shadow";

// ビルドは 1 つ、環境は 2 つ。下のどの行もコンパイル時の違いではありません。
builder.Services.AddSingleton<IMailSender>(sp =>
    caged ? new NoOpMailSender() : sp.GetRequiredService<SmtpMailSender>());
builder.Services.AddDbContext<ShopContext>(o =>
    o.UseSqlServer(builder.Configuration[caged ? "Db:ReadReplica" : "Db:Primary"]));
builder.Services.Configure<PaymentOptions>(
    builder.Configuration.GetSection(caged ? "Payments:Sandbox" : "Payments:Live"));
```

比較器は丁寧に書く価値のある部分です。この取り組み全体が信号を出すか雑音の壁を出すかがここで決まります。比べる前に両方の応答を正規化し、2 つの呼び出しが共有する相関 id で比較ごとにキーを付け、再現できるだけのリクエストとともに不一致を記録します。

```csharp
static JsonNode Normalise(JsonNode answer)
{
    // ここにある値はリクエストのたびに変わり、何の意味もありません。
    // これを取り除いたあとに残るものが、不一致が本当に指している部分です。
    answer["generatedAt"] = null;
    answer["requestId"] = null;
    foreach (var line in answer["lines"]!.AsArray()) line!["rowVersion"] = null;
    return answer;
}
```

あとはいつもの土台です。分かれ目には `IConfiguration` とオプションパターンを使い、シャドウも他と同じようにデプロイされ見守られるよう health probe と readiness probe を置き、成績表に応答本文だけでなくレイテンシやエラー率も入るよう両方の版に同じ指標とトレースを付けます。不一致率が十分に長くゼロのままだったなら、昇格はルーティングの変更 1 つであり、トラフィックを受けるようになる版は、すでに暗がりでその仕事をしてきた版です。
