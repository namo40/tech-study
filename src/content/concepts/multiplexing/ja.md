## いつ使うか

多重化は、切り替えて使う機能というより、すでに話しているプロトコルの性質です。ですから問うべきことは二つあります。いま作っている呼び出しは多重化が助けになる形をしているか、そしてスタックのどこかがその性質をひそかに奪っていないか。

- p95 が跳ね上がるのに p50 が動かないときに読む価値があります。中央値は問題なく見えて尾だけが悪いという形は、共有資源の前にできた列が生む典型的な絵です。クライアントが HTTP/1.1 で、一つのページや一つのハンドラーが同じホストへ小さな呼び出しを八つ出すなら、八つ目はサーバーが忙しいかどうかに関係なく前の七つを待ちます。
- 一つの画面が小さな部品をたくさん必要とするときに見てください。ウィジェットを十二個集めるダッシュボード、関連エンティティを一緒に引く詳細ページ、四つの上流から答えを組み立てるサービスは、どれもリクエスト三つに接続一つという同じ絵の数字を大きくしただけです。多重化はその合計を最大値に変えます。
- サービス間の呼び出しでは特に効きます。ブラウザーが手に入れた当て木が、ここでは手に入らないからです。ブラウザーはオリジンごとに接続を六本開くことで HTTP/1.1 の問題を長らく隠してきましたが、それは一本の中で勝ち取った並列性ではなく接続で買った並列性です。`HttpClient` は既定でそうはせず、持っているプールも同時実行より再利用を狙った大きさです。
- 長く生きるレスポンス一つが線を占有してしまう場面でも必要です。ストリーミングのエンドポイント、サーバー送信イベントのフィード、ロングポーリングは、HTTP/1.1 では生きている間ずっと接続を一本占有します。ほかの全員が必要としているものを消費することになります。HTTP/2 では多くのうちの一ストリームにすぎません。
- gRPC を検討しているなら、多重化は前提です。gRPC は定義上 HTTP/2 であり、一つのチャネル上の同時呼び出しと開いたまま保たれる双方向ストリームという呼び出しモデル全体が、トランスポートが多重化するという前提の上に立っています。一つのサービスが一つの `GrpcChannel` を共有する形は、近道ではなく意図された使い方です。
- 遅いサーバーを直すために持ち出さないでください。多重化が取り除くのは、リクエストがほかのリクエストを待つ時間です。リクエストが答えを作るのに使う時間には何の影響もありません。場面の遅い呼び出しが 1 秒かかった理由が背後のクエリに 1 秒かかることなら、場面のどの段階もその 1 秒より早くは終わりません。

## 注意点

- HTTP 層の head-of-line blocking は消えますが、TCP 層のものは残ります。それらのストリームはすべて一本の TCP 接続に乗り、TCP はバイトを順番どおりに届けます。パケットを一つ失うと、再送が終わるまですべてのストリームが止まります。その後ろのバイトを上へ渡せないからです。きれいな網では見えませんが、損失の多いモバイル回線では HTTP/1.1 の接続を複数使うより HTTP/2 のほうが遅くなることさえあります。HTTP/3 が TCP ではなく QUIC の上を走る理由は、まさにこの一点です。
- 接続が一本ということは、輻輳ウィンドウも一つということです。すべてのストリームが同じ帯域の割り当てを取り合うので、非常に大きなレスポンスがいくつかあるだけで同じ線を分け合う小さなレスポンスが飢えることがあり、開いたばかりの接続はその上のすべてのストリームに対して同時に遅くなります。プロトコルには優先度付けがありますが、実装の対応がまちまちで、計画の根拠にできるほどではありません。
- 接続上の同時実行には上限があり、その値を決めるのはサーバー側です。`SETTINGS_MAX_CONCURRENT_STREAMS` は相手が広告する数値で、そこに達すると以降のリクエストは HTTP/1.1 のときとまったく同じようにクライアント側で列を作ります。Kestrel の既定値は 100 です。一つのページには十分で、強くファンアウトするサービスには小さい値ですから、無制限だと思い込むより実際の値を知っておくほうが役に立ちます。
- パイプライニングは有効化を検討する選択肢ではありません。場面に登場するのは、それが教訓的な失敗だからです。リクエストは解放しましたがレスポンスの順序は残し、その結果、詰まりを取り除くのではなく移しました。しかも中間装置が入るとひどく壊れたため、クライアントは無効にし、二度と戻しませんでした。有効にするかどうか悩んでいるなら答えは「いいえ」で、本当に欲しいものは HTTP/2 です。
- 自分とサーバーの間に何があるかを確かめます。ロードバランサーやリバースプロキシ、サービスメッシュのサイドカーが HTTP/2 を終端して先を HTTP/1.1 で話すなら、多重化は縁までで、その先には列があります。それが必ず間違いというわけではありません。縁の先の区間はたいてい短く、そこの接続プールは大きいからです。ただ、その性質がオリジンまで届くと思い込むより、どこで終わるかを知っておくほうが安全です。
- 接続が減ると、障害の出方も負荷分散も変わります。一本がすべてを運ぶということは、その一本を失えばすべてを一緒に失うということであり、L4 のロードバランサーはリクエストではなく接続を分けるので、長く生きる多重化接続は自分のトラフィック全部を最初につながったバックエンドに固定します。どちらもたいていは受け入れられますが、誰も口に出さなければどちらも驚きになります。

## .NET では

- クライアント側の振る舞いは `SocketsHttpHandler` にあります。バージョンとポリシーをリクエストかクライアントに指定しますが、`HttpVersion.Version20` だけでは交渉に失敗すると静かに下がる希望値にとどまることを覚えておきます。交渉の失敗を列ではなくエラーにするのは `RequestVersionExact` です。

```csharp
var handler = new SocketsHttpHandler
{
    EnableMultipleHttp2Connections = true,
    PooledConnectionLifetime = TimeSpan.FromMinutes(2),
};

var client = new HttpClient(handler)
{
    DefaultRequestVersion = HttpVersion.Version20,
    DefaultVersionPolicy = HttpVersionPolicy.RequestVersionOrHigher,
};
```

- 知っておくべき設定は `EnableMultipleHttp2Connections` です。これがないと一つの `HttpClient` はエンドポイントごとに HTTP/2 接続をちょうど一本しか使わず、その接続が相手のストリーム上限に達するとリクエストは待ちます。有効にすると、ハンドラーは列を作る代わりに接続をもう一本開きます。ファンアウトするクライアントでは有効にします。
- `HttpClient` は共有し、ハンドラーは `IHttpClientFactory` に持たせます。多重化はハンドラーの中の接続の性質なので、呼び出しごとに作ったクライアントはその性質をまったく受け取りません。ファクトリーが推奨になった理由であるソケット枯渇の話を、反対側から見たものです。
- サーバー側では Kestrel が何を受け入れるかを決めます。HTTP/1.1 のクライアントが動き続けるよう既定値は `Http1AndHttp2` で、ストリーム上限は接続ごとであり、すべてのクライアントに同じように適用されます。

```csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.ConfigureEndpointDefaults(endpoint =>
    {
        endpoint.Protocols = HttpProtocols.Http1AndHttp2;
    });
    options.Limits.Http2.MaxStreamsPerConnection = 200;
});
```

- 平文の区間には、代わりに交渉してくれるハンドシェイクがありません。HTTP/2 は普通 TLS ハンドシェイク中の ALPN で合意されるので、素の `http://` エンドポイントにはどのプロトコルを話すかを直接伝える必要があります。サーバー側のそのエンドポイントに `HttpProtocols.Http2` を、クライアント側に `HttpVersionPolicy.RequestVersionExact` を指定します。クラスター内の gRPC サービスは、たいていこの状況です。
- gRPC ではアドレスごとに `GrpcChannel` を一つ作り、それを使い続けます。チャネルが接続を握っていて、その上の呼び出しはすべてストリームであり、効いてくる同時実行の上限は呼び出す側のコードではなくサーバーの `MaxStreamsPerConnection` です。負荷試験が怪しいほどきりのよい同時呼び出し数で頭打ちになるなら、まずその設定を見ます。
