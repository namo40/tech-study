場面の 3 段目はクエリの前に規則カードを置き、ちょうど 2 つのことを見せます。形式の崩れた値は入り口で追い返され、データベースへの往復を 1 回も使いません。そのあと、形式的に完璧な値が同じカードをそのまま通り抜け、それでも data スロットに無害に収まります。その値が届いたチャネルは、もともと何かを実行するチャネルではなかったからです。どちらの読み取りも大事で、2 つ目こそが、このページが答えではなく連れとして存在する理由です。

検証が本当に得意なのは、システムがそもそも考慮する値の集合を狭めることです。注文 id は `Guid`、ページサイズは 1 から 100 の整数、国コードは大文字 2 文字、メールには形と最大長があり、アップロードにはサイズとコンテンツタイプがあります。どれもドメインについての言明で、境界で強制すれば残りのコードはその問いを止められます。得られるのはセキュリティだけではありません。下流の分岐が減り、エラーメッセージがよくなり、何かが壊れうる面積が小さくなります。

検証がどれだけ効くかを決めるのは、許可リスト優先という原則です。危険だと思うものを並べるのではなく、受け入れるものを述べて残りを断ります。拒否リストは敵対的入力の空間全体についての主張で、エンコーディングや正規化形式、見た目のよく似たユニコード文字、新しいパーサーが現れるたびに、その主張を正しく保ち続けなければなりません。許可リストは、あなたが実際に知っている自分のドメインについての主張です。「大文字 ASCII 2 文字」は確信できる規則です。「今のところ危険だと思っている文字以外はすべて」は、年を取るのが下手で、静かに失敗する規則です。

検証が助けにならない場所は、場面がわざと描いてみせる場合です。形式規則を満たした攻撃も、やはり攻撃です。規則はあなたが想像した入力に合わせて書かれていて、その値が受け入れられたあとに何をするかについては何も言いません。だからこそ、クエリを安全にするのは検証ではありません。パラメーター化は構造的な性質です。値が通るチャネルをパーサーがコードとして読まないので、その中身は興味のないものになります。それが成り立っていれば、検証を通り抜けた敵対的な値は、ただ誰とも一致しない名前にすぎません。成り立っていなければ、世界一厳しい形式規則も、巧妙なエンコーディングひとつで意味を失います。

入力が解釈器と出会う他のあらゆる場所でも、関係は同じです。検証はフィルターで、防御は、値が HTML に届くときの文脈を踏まえた出力エンコーディング、値が列や並び順を名指すときの識別子の許可リスト、値がファイルを名指すときの安全なパス結合と正規化の確認、値が逆シリアル化の対象を名指すときの型の許可リストです。どの場合も形は同じです。ノイズを減らすために検証し、中身が受け手の実行を変えられないようにエンコードするかバインドします。

検証が本物かどうかは、実務的な 2 点で決まります。第一に、サーバーで動く必要があります。クライアント側の規則はユーザー体験のための機能で、往復を節約しますが何も止めません。問題になるリクエストは、そもそもあなたのフォームを通っていないからです。第二に、リクエストを表すモデルの上で、端で一度だけ動く必要があります。呼び出しの連鎖に散らばった検証は、いつか誰かが飛ばす検証です。同じ値を 4 か所で検証し直すのは、4 つの規則がずれていく近道です。リクエストを型にバインドし、その型を検証し、その下ではすでに範囲内だと分かっている値だけを扱わせます。

ASP.NET Core ではそれがモデル検証です。データ注釈が形式と長さと範囲を宣言的に受け持ち、`IValidatableObject` や検証ライブラリが複数のプロパティにまたがる規則を受け持ち、`ApiController` はモデルが無効なら problem details 本文とともに 400 を自動で返します。エンドポイントの本体は、通った入力に対してだけ動く形になります。規則はハンドラーではなくモデルのそばに置き、メッセージに内部事情を混ぜず、型システムに背負えるだけ背負わせます。`Guid` のパラメーターに 16 進数の規則は要らず、`enum` にどの値が存在するかの規則は要りません。

正直なまとめは、字幕が言うとおりです。ノイズを締め出すために検証します。そして検証が見逃すからこそ、パラメーター化し、エンコードし、アカウントを狭めるのです。
