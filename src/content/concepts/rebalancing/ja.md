## いつ使うか

- 分割されたデータの下でノードの集合が変わるときはいつでも使います。きっかけはそれだけで、形は 4 つあります。ノードが参加して分け前を渡す必要があるとき、ノードが去ってそのパーティションの行き先が要るとき、ノードが死んでその分け前をどこかに作り直すとき、そして、あるパーティションが騒がしくなり、隣から引き離すほうが我慢するより安くつくときです。
- **役に立たなかったスケールアウト。** 分割されたストアにマシンを 1 台足しても、それだけでは何も買えません。リクエストはパーティションのある場所へ行き、パーティションは相変わらず元の場所にあるからです。新しいノードはゼロで遊び、古いノードは限界に留まったままで、データが動くまで容量のグラフは動きません。スケールアウトがただに見えたなら、まだ終わっていないということです。
- **逆から回した同じ作業、スケールイン。** まだパーティションを所有しているノードは落とせません。だから計画的な撤去は期限つきのリバランシングです。先にパーティションを新しい所有者へ流し、Map に去るノードの名前がもう出てこないことを確かめ、それからノードを外します。
- **ホットスポットの解消。** 2 つのパーティションが数の上では完璧に釣り合いながら、トラフィックでは大きく偏ることがあります。騒がしいほうを静かなノードへ移せば、パーティションキーに触れずに症状を直せます。キーがすでに本番に乗ったあとで使える、いちばん安い訂正です。
- **障害時の置き換えのあとで。** 置き換えのノードは空で到着します。そのノードが分け前を受け取るまで、システムは意図した散らばりよりノード 1 つ分足りない状態です。次に誰が答えるかは failover が決め、絵を本来の姿に戻すのがリバランシングです。
- ただし、常時回す趣味にはしないでください。移動の一つひとつが実在のリンクを通る実在のバイトであり、同じディスクを本番トラフィックと奪い合います。偏りが移動より高くつくときにリバランスするのであって、カレンダーを見てやるのではありません。

## 注意点

- 動かすのはパーティションであって、行を 1 つずつではありません。リバランシングの単位はパーティショニングの単位です。パーティションは Map が名前を呼ぶもの、ロックが覆うもの、ノードが所有すると言えるものです。行を 1 つずつ動かすと、最後の 1 行が落ち着くまで Map は何がどこにあるかを言えなくなり、その区間こそシステムが答えられない区間になります。
- 移動の回数を数えてください。その回数が設計そのものです。キーをノード数で割った余りでハッシュする方式は、ノードが変わるたびにデータの大半を混ぜ直します。4 台から 5 台へ行くだけで全体の 80% 近くが動くので、日常のスケール操作がマイグレーションになってしまいます。安定した方式はそれを避けるためにあります。小さな固定パーティションをたくさん作ってノードに割り当てておけば、参加 1 つで動くのは割り当てが少しだけで、ほかはそのままです。ハッシュリングは隣り合う 2 点の間のキーだけを動かします。どちらもコストを、実際に変わった分だけに比例させます。
- データが動いている間も応答を続けます。それを可能にするのが Map です。Map はいまの所有者を名指しし、バージョンが付いていて、古い写しを持つクライアントは失敗ではなく案内し直しを受けます。それがなければ移動の一つひとつがコピーの長さぶんの障害になり、残る選択肢は停止時間だけになります。
- コピーに制限をかけます。リバランシングのトラフィックと本番のトラフィックは、同じディスク、同じリンク、同じページキャッシュを欲しがります。制限のないリバランシングは、トラフィック急増とそっくりに見える自作の障害です。レート制限を付けて一度に 1 つずつ動かすほうが、早く終わる代わりにサービスまで連れていく嵐よりましです。
- 振動を警戒します。短いスパイクに反応する自動リバランサは、パーティションを移してはスパイクが去ると戻し、何も得ずに二度払います。信号をならし、偏りが続くことを条件にし、同じパーティションを動かせる間隔に下限を置きます。
- 途中で失敗した移動への答えを用意しておきます。コピーが死ぬことも、宛先が消えることも、切り替えがタイムアウトすることもあります。すべての移動は、どの瞬間にも所有者がはっきりしていなければなりません。実務ではそれは、新しい所有者が完全になったと証明されるまで古い所有者が応答し続けるということであり、捨てられたコピーは 2 つ目の真実ではなくゴミだということです。
- 一度のリバランシングで 2 つのことを変えないでください。パーティションを動かすことと、パーティションキーを変えることは、失敗の形が違う別々の作業です。両方を同時にやると、どちらもきれいには戻せません。

## .NET では

これは自分で書くコードというより、知っておく価値のあるプラットフォームの挙動です。Azure Cosmos DB は物理パーティションがストレージやスループットの上限を超えると分割し、分かれた半分を自分で動かします。Service Fabric はクラスターの釣り合いを取るためにレプリカをノード間で動かします。Kafka はメンバーが入るたび出るたびにコンシューマーグループへパーティションを割り当て直しますが、これは同じ発想のメッセージ側の兄弟です。3 つとも、アプリケーションのコードには同じものとして見えます。所有が落ち着くまでの短い案内し直し、タイムアウト、再試行です。

なので .NET 側の接点はクライアントで、目指す形はやみくもに再試行するクライアントではなく、引き直すクライアントです。

```csharp
// Map が真実なので、古い答えは失敗する理由ではなく、もう一度見る理由です。
// 同じ接続で再試行しても、同じ空のノードに当たるだけです。
public async Task<T> ReadAsync<T>(Guid key, Func<string, Task<T>> read, CancellationToken ct)
{
    for (var attempt = 0; ; attempt++)
    {
        var owner = _map.OwnerOf(key);
        try
        {
            return await read(owner);
        }
        catch (PartitionMovedException) when (attempt < 3)
        {
            await _map.RefreshAsync(ct);
        }
    }
}
```

Cosmos DB の SDK はすでにそれをやってくれます。だからそちらでの実際的な助言は、長生きするクライアントを 1 つ置き、パーティションマップをその中に持たせることです。

```csharp
// アプリが生きている間クライアントは 1 つ。パーティションマップをキャッシュし、
// 物理パーティションが分割されると更新するので、分割は見えません。
services.AddSingleton(_ => new CosmosClient(connectionString, new CosmosClientOptions
{
    // ここで分割そのものを扱っているわけではありません。これは、忙しいパーティションが
    // 分割に至るまでに返す 429 のための再試行予算です(9 は既定値でもあります)。
    MaxRetryAttemptsOnRateLimitedRequests = 9,
}));
```

メッセージ側の例では、コンシューマーグループのリバランスが名前だけ違う同じ出来事で、痛いのは割り当てが変わるときに処理中だった仕事です。取り上げを無視せずに処理します。

```csharp
var consumer = new ConsumerBuilder<string, byte[]>(config)
    // パーティションを取り上げられる前に、実際に処理した分までコミットします。
    // そうしないと次の所有者がその分をやり直します。
    .SetPartitionsRevokedHandler((c, partitions) => c.Commit())
    .Build();
```

Map を自分で作るなら、小さく、バージョンを付けて、1 つの部品に所有させます。

```csharp
public sealed record PartitionMap(int Version, IReadOnlyDictionary<int, string> Owners)
{
    public string OwnerOf(Guid key) => Owners[Partition(key)];

    // ノードよりずっと多いパーティションを、ストアの一生のあいだ固定します。
    // そうすればノードが変わって動くのは割り当てで、データの境界ではありません。
    private static int Partition(Guid key) => (int)((uint)Hash(key) % 4096);
}
```

ノード 8 台にパーティション 4096 個なら、9 台目を足すときに動くのは割り当ての 9 分の 1 ほどで、残りは触れられないままです。それが要点です。パーティションの数は一度決めると変えにくく、ノードの数は頻繁に変わり、安くあるべきです。始めるときにその比を正しく取っておくことが、その後のすべてのリバランシングをプロジェクトではなく日常の作業にしてくれます。
