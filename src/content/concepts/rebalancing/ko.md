## 언제 쓰나

- 분할된 데이터 아래에서 노드 집합이 바뀔 때마다 씁니다. 계기는 그것뿐이고, 모습은 네 가지입니다. 노드가 참여해서 제 몫을 받아야 할 때, 노드가 떠나면서 그 파티션들이 갈 곳을 찾아야 할 때, 노드가 죽어서 그 몫을 어딘가에 다시 세워야 할 때, 그리고 한 파티션이 시끄러워져서 이웃에게서 떼어 놓는 편이 참는 것보다 쌀 때입니다.
- **아무 도움이 안 된 확장.** 분할된 저장소에 기계를 한 대 더해도 그것만으로는 아무것도 사지 못합니다. 요청은 파티션이 있는 곳으로 가고, 파티션은 여전히 있던 자리에 있기 때문입니다. 새 노드는 0에서 놀고 옛 노드들은 한계에 머물러 있으며, 데이터가 움직이기 전까지 용량 그래프는 꿈쩍하지 않습니다. 확장이 공짜처럼 보였다면 아직 끝나지 않은 것입니다.
- **거꾸로 돌린 같은 작업, 축소.** 파티션을 여전히 소유한 노드는 끌 수 없습니다. 그래서 계획된 제거는 기한이 있는 재배치입니다. 먼저 파티션들을 새 소유자에게 흘려보내고, Map에 떠나는 노드의 이름이 더 남아 있지 않은지 확인한 뒤에야 그 노드를 치웁니다.
- **핫스팟 해소.** 두 파티션이 개수로는 완벽하게 균형이면서 트래픽으로는 심하게 치우칠 수 있습니다. 시끄러운 쪽을 한산한 노드로 옮기면 파티션 키를 건드리지 않고 증상을 고칠 수 있습니다. 키가 이미 운영에 올라간 뒤에 쓸 수 있는 가장 싼 교정입니다.
- **장애 대체 뒤에.** 대체 노드는 비어서 도착합니다. 그 노드가 몫을 받기 전까지 시스템은 의도한 분산보다 노드 하나가 모자란 상태입니다. 다음에 누가 답할지는 failover가 정하고, 그림을 원래 의도대로 되돌리는 일이 재배치입니다.
- 다만 상시로 돌리는 취미로는 삼지 마세요. 이동 하나하나가 실제 링크를 지나는 실제 바이트이고, 같은 디스크를 두고 운영 트래픽과 다툽니다. 불균형이 이동보다 비쌀 때 재배치하고, 일정표를 보고 하지는 않습니다.

## 주의점

- 옮기는 것은 파티션이어야 하고, 행 하나하나여서는 안 됩니다. 재배치의 단위는 파티셔닝의 단위입니다. 파티션은 Map이 이름을 부르는 대상이고, 잠금이 덮는 대상이고, 노드가 소유한다고 말할 수 있는 대상입니다. 행을 한 번에 하나씩 옮기면 마지막 행이 내려앉기 전까지 Map은 무엇이 어디 있는지 말할 수 없게 되고, 그 구간이 바로 시스템이 답할 수 없는 구간입니다.
- 이동 횟수를 세세요. 그 횟수가 곧 설계입니다. 키를 노드 수로 나눈 나머지로 해싱하는 방식은 노드가 바뀔 때마다 데이터 대부분을 다시 섞습니다. 노드 넷에서 다섯으로 갈 때 전체의 80% 가까이가 움직이니, 일상적인 확장이 마이그레이션이 되어 버립니다. 안정적인 방식들은 그것을 피하려고 있습니다. 작은 고정 파티션을 많이 만들어 노드에 배정해 두면 참여 하나가 배정 몇 개만 옮기고 나머지는 그대로 둡니다. 해시 링은 인접한 두 지점 사이의 키만 옮깁니다. 둘 다 비용을 실제로 바뀐 만큼에 비례하게 만듭니다.
- 데이터가 움직이는 동안에도 계속 응답합니다. 그것을 가능하게 하는 것이 Map입니다. Map은 지금의 소유자를 말하고, 버전이 붙어 있고, 옛 사본을 쥔 클라이언트는 실패가 아니라 재안내를 받습니다. 그것이 없으면 이동 하나하나가 복사 길이만큼의 장애가 되고, 남는 선택지는 점검 창뿐입니다.
- 복사에 제한을 겁니다. 재배치 트래픽과 운영 트래픽은 같은 디스크, 같은 링크, 같은 페이지 캐시를 원합니다. 제한 없는 재배치는 트래픽 급증과 똑같아 보이는, 스스로 낸 장애입니다. 속도 제한을 걸고 한 번에 하나씩 옮기는 편이, 더 빨리 끝나면서 서비스까지 데려가는 폭풍보다 낫습니다.
- 진동을 경계합니다. 짧은 급증에 반응하는 자동 재배치기는 파티션을 옮겼다가 급증이 지나가면 도로 옮겨 오면서, 아무것도 얻지 못한 채 비용만 두 번 냅니다. 신호를 눌러 주고, 불균형이 일정 시간 이어지기를 요구하고, 같은 파티션을 얼마나 자주 옮길 수 있는지에 하한을 둡니다.
- 중간에 실패한 이동에 대한 답을 준비해 둡니다. 복사가 죽을 수도, 대상이 사라질 수도, 전환이 시간 초과될 수도 있습니다. 모든 이동은 매 순간 소유자가 분명해야 합니다. 실무에서 그것은 새 소유자가 완전해졌음이 증명되기 전까지 옛 소유자가 계속 응답한다는 뜻이고, 버려진 복사본은 두 번째 진실이 아니라 쓰레기라는 뜻입니다.
- 한 번의 재배치가 두 가지를 바꾸게 두지 마세요. 파티션을 옮기는 일과 파티션 키를 바꾸는 일은 실패 양상이 다른 별개의 작업이고, 둘을 한꺼번에 하면 어느 쪽도 깔끔하게 되돌릴 수 없습니다.

## .NET에서는

이것은 대체로 직접 작성하는 코드라기보다 알아 둘 만한 플랫폼 동작입니다. Azure Cosmos DB는 물리 파티션이 저장소나 처리량 한계를 넘어서면 쪼개고, 그렇게 나뉜 반쪽들을 스스로 옮깁니다. Service Fabric은 클러스터 균형을 맞추려고 복제본을 노드 사이에서 옮깁니다. Kafka는 구성원이 들어오거나 나갈 때마다 컨슈머 그룹에 파티션을 다시 배정하는데, 이는 같은 발상의 메시지 쪽 형제입니다. 셋 다 애플리케이션 코드에는 같은 모습으로 보입니다. 소유가 자리를 잡는 동안의 짧은 재안내, 시간 초과, 재시도입니다.

그래서 .NET 쪽 접점은 클라이언트이고, 목표로 삼을 모양은 무턱대고 재시도하는 클라이언트가 아니라 다시 조회하는 클라이언트입니다.

```csharp
// Map이 진실이므로, 오래된 답은 실패할 이유가 아니라 다시 볼 이유입니다.
// 같은 연결로 재시도해 봐야 같은 빈 노드를 다시 만날 뿐입니다.
public async Task<T> ReadAsync<T>(Guid key, Func<string, Task<T>> read, CancellationToken ct)
{
    for (var attempt = 0; ; attempt++)
    {
        var owner = _map.OwnerOf(key);
        try
        {
            return await read(owner);
        }
        catch (PartitionMovedException) when (attempt < 3)
        {
            await _map.RefreshAsync(ct);
        }
    }
}
```

Cosmos DB SDK는 이미 그렇게 해 줍니다. 그래서 그쪽에서 실질적인 조언은 오래 사는 클라이언트를 하나 두고 파티션 맵을 그 안에 쥐게 하라는 것입니다.

```csharp
// 앱이 사는 동안 클라이언트 하나. 파티션 맵을 캐시하고 물리 파티션이
// 쪼개지면 갱신하므로, 분할이 보이지 않습니다.
services.AddSingleton(_ => new CosmosClient(connectionString, new CosmosClientOptions
{
    // 분할은 영구 실패가 아니라 재시도 가능한 실패로 나타납니다.
    MaxRetryAttemptsOnRateLimitedRequests = 9,
}));
```

메시지 쪽 사례에서는 컨슈머 그룹 재배치가 이름만 다른 같은 사건이고, 아픈 곳은 배정이 바뀔 때 처리 중이던 작업입니다. 회수를 무시하지 말고 처리합니다.

```csharp
var consumer = new ConsumerBuilder<string, byte[]>(config)
    // 파티션을 빼앗기기 전에 실제로 처리한 데까지 커밋합니다.
    // 그러지 않으면 다음 소유자가 그만큼을 다시 처리합니다.
    .SetPartitionsRevokedHandler((c, partitions) => c.Commit())
    .Build();
```

Map을 직접 만든다면 작게, 버전을 붙여서, 한 구성 요소가 소유하게 둡니다.

```csharp
public sealed record PartitionMap(int Version, IReadOnlyDictionary<int, string> Owners)
{
    public string OwnerOf(Guid key) => Owners[Partition(key)];

    // 노드보다 훨씬 많은 파티션을 저장소의 수명 내내 고정해 둡니다. 그러면
    // 노드가 바뀔 때 움직이는 것은 배정이지 데이터 경계가 아닙니다.
    private static int Partition(Guid key) => (int)((uint)Hash(key) % 4096);
}
```

노드 여덟 대에 파티션 4096개라면 아홉 번째를 더할 때 배정의 8분의 1 남짓만 움직이고 나머지는 손대지 않은 채로 남습니다. 그것이 핵심입니다. 파티션 개수는 한 번 정하고 나면 바꾸기 어렵고, 노드 개수는 자주 바뀌며 싸야 합니다. 시작할 때 그 비율을 제대로 잡아 두는 것이, 이후의 모든 재배치를 프로젝트가 아니라 일상 작업으로 만들어 줍니다.
