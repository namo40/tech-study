## いつ使うか

- ひとつのエンティティが多くの項目へ散らばっているときに使います。ある商品が詳細のペイロードとしても、一覧ページ三か所の行としても、価格の断片としても、検索結果としてもキャッシュされていて、その商品を直せば五つすべてが引き下がらなければなりません。キーで消すには書き込みの時点で五つのキーをすべて知っている必要がありますが、書き込みの経路はそれをほとんど知りません。五つすべてに `product:42` を付けておけば、その知識は、項目の形がまだ目の前にある充填の時点で貼るラベルに変わります。
- ページや断片のキャッシュには粗い無効化が要りますし、そこでは粗いことが正しい粒度です。キャッシュされた応答のキーは経路とクエリ文字列と変化要因のヘッダーの組み合わせなので、キーの空間は組み合わせで膨らみ、誰も並べ切れません。カタログ領域の応答に `catalog` のタグを付けておけば、公開の操作はそこで作られたすべての変種へ届く取っ手をひとつ手にします。
- 項目が派生物で、キーを導き出せないときに使います。一覧も件数も上位 N の表も集計も、呼び出し側から来た引数で作られたクエリの結果です。入力のひとつを変える書き込みには、どの集計がその入力を吸い込んだのかを組み立て直す方法がありません。集計をキャッシュしたときに付けたタグが、その関係が存在したことを残す唯一の記録です。
- 新しいキーの空間を作らずに cache-version の効果だけが欲しいときに選びます。バージョンの方式は世代の番号をキーに入れ、古い項目が期限で消えるのを待って同じ問題を解きます。安上がりですが、ごみがしばらく残ります。タグは孤児にするのではなく消すので、古い項目が実際のメモリを占めるときや、読み手が古い値へそもそも届いてはいけないときはタグを選びます。

## 注意点

- タグは購読ではありません。ひとまとまりの項目を一度に落とす手段であって、すべてのノードが同じ瞬間に受け取ったイベントのように振る舞うと期待するなら誤解です。削除はキャッシュの実装が自分のやり方で取りまとめ、二段目の格納庫は自分の都合で伝えるので、タグがその隙間を閉じてくれたと仮定せず、二つのインスタンスがまだ食い違いうる区間を書き留めておくほうが確かです。
- タグが広いほど、あとに残る穴が大きくなります。カタログの項目すべてに付けた `catalog` のようなタグは無効化を簡単に正しくしてくれる代わりに、価格を一行直しただけの操作を領域全体の冷えたキャッシュに変えます。しかもその結果は、よりによって誰かが見ている瞬間に、データベースへの殺到として届きます。書き込みひとつが正当に壊してよい範囲に合わせてタグの大きさを決め、広いタグの隣に狭い `product:42` を置いて、よくある場合が小さい槌を使うようにしてください。
- 分散キャッシュでは、タグは維持の費用を取ります。格納庫はタグから項目への逆向きの対応を抱えるか、毎回走査しなければならず、それは充填ごとに増える書き込みであり、追い出しごとに増える仕事です。共有の格納庫ではその索引も共有なので、おしゃべりなタグの設計はそのインスタンスを使う全員の遅延として現れます。項目あたり数個までなら払えますし、タグ付けが自由記述になった時点で払えなくなります。
- 歯止めのないタグ付けは、無効化をふたたび予測できないものにします。出発点だったその問題へ戻るわけです。チームごとに自分のラベルを考え出せば、項目ひとつが六つを抱えることになり、ある削除がどこまで届くのかを誰も言えなくなり、善意の掃除が無関係な機能を空にします。タグの語彙はキャッシュキーの隣に定義した閉じた一覧として持ち、自由な文字列ではなく識別子からタグを作り、タグをひとつ増やすことは細部ではなく設計の変更として扱ってください。

## .NET では

- `HybridCache` は項目にタグを受け取り、タグで消します。タグ付けは項目が作られる場所で、無効化は書き込みが起きる場所で行われます。

```csharp
// Tags are declared with the entry, at the moment its shape is known.
var product = await cache.GetOrCreateAsync(
    $"product:{id}",
    id,
    async (key, ct) => await repository.GetProductAsync(key, ct),
    tags: [$"product:{id}", $"catalog:{categoryId}", "catalog"],
    cancellationToken: ct);

// The write path names the subject, not the keys.
await cache.RemoveByTagAsync($"product:{id}", ct);

// The broad tag exists for republishing the whole section. Use it deliberately.
await cache.RemoveByTagAsync("catalog", ct);
```

- 出力キャッシュにも応答のための同じ仕掛けがあります。エンドポイントに付けた `[OutputCache(Tags = ["catalog"])]` がそこで作られたキャッシュの変種すべてにラベルを貼り、管理の操作やメッセージのハンドラーから呼ぶ `IOutputCacheStore.EvictByTagAsync("catalog", ct)` がそのすべてを引き下がらせます。追い出す側のコードは経路もクエリ文字列も知る必要がありません。
- タグはキーを作るその場所で一緒に作ります。補助のメソッドが `product:{id}` をキーとして組み立てるなら、タグも同じ場所で組み立てさせてください。そうすれば規約の名前が変わったときに二つの綴りが食い違い、すべての削除が静かに何もしない呼び出しになってしまう事故を防げます。
- タグでの削除は、要求よりもメッセージのハンドラーに置くとよく収まります。トランザクションが確定したあとにドメインのイベントの受け手で実行すれば、巻き戻された書き込みが無駄にキャッシュを空にすることがなく、すべてのインスタンスが同じ引き金を共有します。
