## いつ使うか

- ひとつのストアの負荷や大きさや事故の範囲を縮めなければならず、もっと安い手が残っていないときに使います。パーティショニングは、インデックスで足りないクエリではなく、一台の機械を超えたテーブルへの答えです。この区別が大事なのは、二つのうち片方だけが二本目の接続文字列に見合う問題だからです。
- **横に、容量のために。** どのパートにも同じスキーマ、パートごとに違う行です。各パートが行の分け前、書き込みの分け前、そして行数につれて増えるすべての分け前を担ぎます。ロックはテーブル全体ではなくパートの中で競合し、キャッシュはひとつのパートの意味のある割合を保持し、バックアップやインデックス再構築は与えられた窓の中で終えられる一切れだけを覆います。人々がシャーディングと呼ぶときに指す切り方がこれです。
- **縦に、熱い経路の速さのために。** すべてのリクエストが読む狭い列を、ほとんど誰も読まない広い列から切り離します。説明の塊、直列化されたペイロード、監査の記録、画像といったものです。すると頻繁な読み取りは、キャッシュの一ページに自分をより多く収められる細身の行だけに触れ、広い半身は本当にそれを欲しがる珍しい機会にだけ取ってきます。
- **機能ごとに、独立のために。** キーではなくサービスの境界に沿って引いた線で、テーブルごとに違うストアへ置きます。三つ目の軸であり、パーティショニングと最も呼ばれにくい軸ですが、注文と分析を別々のデータベースに分ける仕事は、行ではなくテーブルについて下す同じ決定です。
- バックアップや復元やインデックス保守が与えられた時間を超えたときに使います。ひとつのテーブルを四時間かけて復元するのは四時間の障害です。同じハードウェアで四つのパートを並行に復元するのは別の話で、壊れなかったパートはそもそも落ちていません。
- 性能とは関係のない理由で、あるテナントや地域や顧客を隔離しなければならないときに使います。テナントごとにパートを持てば「この顧客に属するものを全部消す」が削除ではなくドロップになり、データの所在の要件がクエリの条件ではなくデプロイの決定になります。
- **最初の手としては使わないでください。** インデックス、キャッシュ、読み取りレプリカ、より大きな機械、そしてもう要らないデータを消すことは、いつでも二つ目のパートより安く済みます。しかもそのどれもが火曜日のうちに戻せます。パーティショニングはここで唯一、うまく回った期間が長いほど戻しにくくなる構造の決定です。

## 注意点

- パーティションキーが決定であり、残りはすべて手段です。キーはすべての熱いクエリに入っていなければならず、そうでなければそれらのクエリはすべてのパートを訪ねることになります。キーは負荷を均等に散らさなければならず、そうでなければひとつのパートがシステムを背負います。キーは決して変わってはならず、そうでなければ値をひとつ直すことがストアをまたぐ行の移動になります。永久のもののつもりで選んでください。実際にそうなのですから。
- 日付や時刻のキーは今日を熱いパートにします。新しい行はどれも今日を持っているので、すべての書き込みが同じパートに落ち、ほかは遊びます。紙の上では釣り合って見えた設計が、忙しいテーブルひとつへ崩れ戻るのです。時間ベースのパーティショニングは、アクセスのパターンも時間ベースであるとき、つまり保存期間とアーカイブ、範囲で読む追記専用のテレメトリに合います。ワークロードが「最近のものを、絶えず」になった瞬間に誤りになります。
- カーディナリティが低いとパートの数に上限ができます。異なる値が六つのキーは、機械をいくら買っても六つのパートを超えられませんし、元から分布が偏ったキーは、その偏りのまま大きさの偏ったパートを作ります。機械を数える前に異なる値を数えてください。
- キーを持たないクエリはすべてのパートを訪ね、答えを合わせなければなりません。それは実費のかかる実際の作業であり、安い照会ひとつを、いちばん遅いパートが遅延を決める fan-out に変えてしまいます。速くあるべきクエリを中心にキーを設計し、遅くてよいクエリには fan-out を受け入れます。あるいはそれらのために、別のキーで持った複製を用意します。
- トランザクションと一意制約はパートの境界で止まります。二つのパートにある二行をデータベースが原子的に更新することはできませんし、一意インデックスはパートをまたげません。だから一意性は、アプリケーションか別のストアが守るものになります。パートをまたぐ外部キーは、そもそも強制できなくなります。
- 縦の分割は、行全体を欲しがる読み取りごとに結合か二度目の取得を支払います。それが意図して結んだ取引です。珍しい読み取りが払うことで、ありふれた読み取りが払わずに済むのですから。ただし熱い経路で二つの半身を両方読み始めた瞬間、その取引はもうよい取引ではありません。
- 想像できるパートではなく、運用できるパートを数えてください。パートのひとつひとつが、監視し、バックアップし、パッチを当て、フェイルオーバーし、午前三時に頭で追う対象です。チームが実際に回せる四つのパートは、たいてい図の中にしかない六十四のパートに勝ちます。
- 後からデータを動かすほうが高くつく話です。キーやパート数を変えることは、システムがトラフィックを受けている最中にストアをまたいで行を書き直すことであり、移動の途中で読む側が何を見るのかまで決めておく必要があります。キーを永久のもののつもりで選ぶ理由がこれで、consistent hashing と rebalancing がそれぞれの主題として別にある理由もこれです。

## .NET では

縦のパーティショニングには EF Core の直接の支援があります。二つのエンティティが、互いの存在を知らないままひとつのテーブルとひとつの行を分け合えるからです。テーブル分割は、この場面の三段目のモデル版です。

```csharp
// 広い半身は、同じテーブルと同じキーを共有する別のエンティティです。だから
// Product を照会しても、頼まないかぎり塊が載ることはありません。
modelBuilder.Entity<Product>(b =>
{
    b.ToTable("Products");
    b.HasOne(p => p.Details).WithOne()
        .HasForeignKey<ProductDetails>(d => d.Id);
});

modelBuilder.Entity<ProductDetails>().ToTable("Products");
```

すると狭い半身を読むことが既定になり、広い半身は明示して頼むものになります。

```csharp
// 熱い経路: 塊も、説明も、監査のペイロードもありません。
var summary = await db.Products
    .Where(p => p.CategoryId == categoryId)
    .Select(p => new ProductSummary(p.Id, p.Name, p.Price))
    .ToListAsync(ct);

// 珍しい経路: 誰かが実際にそれを開いたときだけ。
var full = await db.Products
    .Include(p => p.Details)
    .SingleAsync(p => p.Id == id, ct);
```

横のパーティショニングにフレームワークの機能はありません。フレームワークにはあなたのキーがわからないからです。必要なのは、キーから接続文字列への地図と、パートごとにひとつのコンテキストです。

```csharp
public sealed class ShardMap(IReadOnlyList<string> connections)
{
    // キーの規則はひとつの場所に住みます。ほかのすべてはそれを読むだけで、
    // 何も自分で決めません。だから規則を変えることが限られた変更になります。
    public string ConnectionFor(Guid tenantId) =>
        connections[(int)((uint)tenantId.GetHashCode() % connections.Count)];
}

public sealed class OrdersContextFactory(ShardMap map)
{
    public OrdersContext For(Guid tenantId)
    {
        var options = new DbContextOptionsBuilder<OrdersContext>()
            .UseSqlServer(map.ConnectionFor(tenantId))
            .Options;
        return new OrdersContext(options);
    }
}
```

上の規則はキーに範囲を取らずハッシュを使います。その違いが、散らすことと積むことの違いです。日付に範囲を取れば新しい行は全部いちばん最後のパートへ行きますが、テナントにハッシュをかければ散らばります。あわせて、`GetHashCode` はプロセスやランタイムの版をまたいで安定ではないことにも注意してください。実際のシャードの地図は、文字列形式のハッシュのように自分が所有するハッシュを使い、同じキーが来年も同じパートへ解決されるようにします。

マネージドなプラットフォームは配管ではなく形を与えます。Azure SQL Database は、キーの範囲とそのデータベースを持つ shard map manager を備えた elastic database tools を提供します。Azure Cosmos DB はパーティションキーをコンテナー定義の一部にするので、その選択は作成時に宣言され、後から直すことはできません。

```csharp
await database.CreateContainerIfNotExistsAsync(new ContainerProperties(
    id: "orders",
    // 散ることのため、そしてすべての熱いクエリに入っているから選んだキーです。
    // 永久でもあります。変えるには新しいコンテナーと移行が要ります。
    partitionKeyPath: "/tenantId"));

// 単一パーティションの読み取り: キーを渡したので、ひとつのパーティションが答えます。
var order = await container.ReadItemAsync<Order>(
    id, new PartitionKey(tenantId), cancellationToken: ct);
```

アクセスのパターンが本当に時間の形をしている時間の形のデータなら、SQL Server 自身のパーティションテーブルが、ひとつの論理テーブルを範囲関数でパーティションに分けて保持します。するとアーカイブが削除ではなくメタデータの操作になります。

```sql
-- ログを埋める DELETE ではなく、スイッチで済ませる保存期間の運用です。
ALTER TABLE Telemetry SWITCH PARTITION 1 TO TelemetryArchive PARTITION 1;
```

目指す形は、場面が終わる場所の形です。ひとつの規則が行のありかを決め、その規則はひとつの場所で読めて、すでにすべての熱いクエリが持ち歩いているものを指しています。パートは同じスキーマに違う行を持つか、同じ同一性に違う列を持つかで、そのどちらであるかは流れた結果ではなく決定でした。そして動いているシステムのどの部分も、パートの数が今日のままであることに寄りかかっていません。パーティショニングされたストアについて確かなことはひとつ、今持っている数より多くのパートが必要になる、ということなのですから。
