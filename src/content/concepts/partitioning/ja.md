## いつ使うか

- 1 つのストアの負荷や大きさや事故の範囲を縮めなければならず、もっと安い手が残っていないときに使います。パーティショニングは、インデックスで足りないクエリではなく、1 台の機械を超えたテーブルへの答えです。この区別が大事なのは、2 つのうち片方だけが 2 本目の接続文字列に見合う問題だからです。
- **横に、容量のために。** どのパートにも同じスキーマ、パートごとに違う行です。各パートが行の分け前、書き込みの分け前、そして行数につれて増えるすべての分け前を担ぎます。ロックはテーブル全体ではなくパートの中で競合し、キャッシュは 1 つのパートの意味のある割合を保持し、バックアップやインデックス再構築は与えられた窓の中で終えられる 1 切れだけを覆います。人々がシャーディングと呼ぶときに指す切り方がこれです。
- **縦に、ホットパスの速さのために。** すべてのリクエストが読む狭い列を、ほとんど誰も読まない広い列から切り離します。説明の塊、直列化されたペイロード、監査の記録、画像といったものです。すると頻繁な読み取りは、キャッシュの 1 ページに自分をより多く収められる細身の行だけに触れ、広い半身は本当にそれを欲しがる珍しい機会にだけ取ってきます。
- **機能ごとに、独立のために。** キーではなくサービスの境界に沿って引いた線で、テーブルごとに違うストアへ置きます。3 つ目の軸であり、パーティショニングと最も呼ばれにくい軸ですが、注文と分析を別々のデータベースに分ける仕事は、行ではなくテーブルについて下す同じ決定です。
- バックアップや復元やインデックス保守が与えられた時間を超えたときに使います。1 つのテーブルを 4 時間かけて復元するのは 4 時間の障害です。同じハードウェアで 4 つのパートを並行に復元するのは別の話で、壊れなかったパートはそもそも落ちていません。
- 性能とは関係のない理由で、あるテナントや地域や顧客を隔離しなければならないときに使います。テナントごとにパートを持てば「この顧客に属するものを全部消す」が削除ではなくドロップになり、データの所在の要件がクエリの条件ではなくデプロイの決定になります。
- **最初の手としては使わないでください。** インデックス、キャッシュ、読み取りレプリカ、より大きな機械、そしてもう要らないデータを消すことは、いつでも 2 つ目のパートより安く済みます。しかもそのどれもが火曜日のうちに戻せます。パーティショニングはここで唯一、うまく回った期間が長いほど戻しにくくなる構造の決定です。

## 注意点

- パーティションキーが決定であり、残りはすべて手段です。キーはすべての熱いクエリに入っていなければならず、そうでなければそれらのクエリはすべてのパートを訪ねることになります。キーは負荷を均等に散らさなければならず、そうでなければ 1 つのパートがシステムを背負います。キーは決して変わってはならず、そうでなければ値を 1 つ直すことがストアをまたぐ行の移動になります。永久のもののつもりで選んでください。実際にそうなのですから。
- 日付や時刻のキーは今日を熱いパートにします。新しい行はどれも今日を持っているので、すべての書き込みが同じパートに落ち、ほかは遊びます。紙の上では釣り合って見えた設計が、忙しいテーブル 1 つへ崩れ戻るのです。時間ベースのパーティショニングは、アクセスのパターンも時間ベースであるとき、つまり保存期間とアーカイブ、範囲で読む追記専用のテレメトリに合います。ワークロードが「最近のものを、絶えず」になった瞬間に誤りになります。
- カーディナリティが低いとパートの数に上限ができます。異なる値が 6 つのキーは、機械をいくら買っても 6 つのパートを超えられませんし、元から分布が偏ったキーは、その偏りのまま大きさの偏ったパートを作ります。機械を数える前に異なる値を数えてください。
- キーを持たないクエリはすべてのパートを訪ね、答えを合わせなければなりません。それは実費のかかる実際の作業であり、安い照会 1 つを、いちばん遅いパートがレイテンシを決める fan-out に変えてしまいます。速くあるべきクエリを中心にキーを設計し、遅くてよいクエリには fan-out を受け入れます。あるいはそれらのために、別のキーで持った複製を用意します。
- トランザクションと一意制約は、パートが別々のデータベースになった時点でパートの境界で止まります。2 つのパートにある 2 行をデータベースが原子的に更新することはできませんし、一意インデックスはパートをまたげません。だから一意性はアプリケーションか別のストアが守るものになり、パートをまたぐ外部キーはそもそも強制できなくなります。1 つのデータベースの中のパーティションテーブルは例外です。それは依然として 1 つの論理テーブルなので、トランザクションも、パーティション列を含む一意インデックスも、これまでどおり働きます。
- 縦の分割は、行全体を欲しがる読み取りごとに結合か 2 度目の取得を支払います。それが意図して結んだ取引です。珍しい読み取りが払うことで、ありふれた読み取りが払わずに済むのですから。ただしホットパスで 2 つの半身を両方読み始めた瞬間、その取引はもうよい取引ではありません。
- 想像できるパートではなく、運用できるパートを数えてください。パートのひとつひとつが、監視し、バックアップし、パッチを当て、フェイルオーバーし、午前 3 時に頭で追う対象です。チームが実際に回せる 4 つのパートは、たいてい図の中にしかない 64 のパートに勝ちます。
- 後からデータを動かすほうが高くつく話です。キーやパート数を変えることは、システムがトラフィックを受けている最中にストアをまたいで行を書き直すことであり、移動の途中で読む側が何を見るのかまで決めておく必要があります。キーを永久のもののつもりで選ぶ理由がこれで、consistent hashing と rebalancing がそれぞれの主題として別にある理由もこれです。

## .NET では

縦のパーティショニングには EF Core の直接の支援があります。2 つのエンティティが、互いの存在を知らないまま 1 つのテーブルと 1 つの行を分け合えるからです。テーブル分割は、このシーンの 3 番目のステップのモデル版です。

```csharp
// 広い半身は、同じテーブルと同じキーを共有する別のエンティティです。だから
// Product を照会しても、頼まないかぎり塊が載ることはありません。
modelBuilder.Entity<Product>(b =>
{
    b.ToTable("Products");
    b.HasOne(p => p.Details).WithOne()
        .HasForeignKey<ProductDetails>(d => d.Id);
});

modelBuilder.Entity<ProductDetails>().ToTable("Products");
```

すると狭い半身を読むことが既定になり、広い半身は明示して頼むものになります。

```csharp
// ホットパス: 塊も、説明も、監査のペイロードもありません。
var summary = await db.Products
    .Where(p => p.CategoryId == categoryId)
    .Select(p => new ProductSummary(p.Id, p.Name, p.Price))
    .ToListAsync(ct);

// 珍しい経路: 誰かが実際にそれを開いたときだけ。
var full = await db.Products
    .Include(p => p.Details)
    .SingleAsync(p => p.Id == id, ct);
```

横のパーティショニングにフレームワークの機能はありません。フレームワークにはそのキーが分からないからです。必要なのは、キーから接続文字列へのマップと、パートごとに 1 つのコンテキストです。

```csharp
public sealed class ShardMap(IReadOnlyList<string> connections)
{
    // キーの規則は 1 つの場所に住み、ほかの何も自分で決めません。この mod-N の
    // 本体は素朴な版です。パート数の変更に耐える規則は consistent hashing と
    // rebalancing を参照してください。
    public string ConnectionFor(Guid tenantId) =>
        connections[(int)((uint)tenantId.GetHashCode() % connections.Count)];
}

public sealed class OrdersContextFactory(ShardMap map)
{
    public OrdersContext For(Guid tenantId)
    {
        var options = new DbContextOptionsBuilder<OrdersContext>()
            .UseSqlServer(map.ConnectionFor(tenantId))
            .Options;
        return new OrdersContext(options);
    }
}
```

上の規則はキーに範囲を取らずハッシュを使います。その違いが、散らすことと積むことの違いです。日付に範囲を取れば新しい行は全部いちばん最後のパートへ行きますが、テナントにハッシュをかければ散らばります。あわせて、`GetHashCode` はデータの置き場所を決めるハッシュとしては間違いだということにも注意してください。`Guid.GetHashCode` は今日たまたま決定的ですが、ランタイムの版をまたいでそうである約束はなく、`string.GetHashCode` はプロセスごとにランダム化されるので、そのやり方でハッシュしたキーは再起動のあと別の場所に落ちます。実際のシャードマップは、sharding のページと同じ `XxHash64` のように自分が所有するハッシュを使い、同じキーが来年も同じパートへ解決されるようにします。

マネージドなプラットフォームは配管ではなく形を与えます。Azure SQL Database は、キーの範囲とそのデータベースを持つ shard map manager を備えた elastic database tools を提供します。Azure Cosmos DB はパーティションキーをコンテナー定義の一部にするので、その選択は作成時に宣言され、後から直すことはできません。

```csharp
await database.CreateContainerIfNotExistsAsync(new ContainerProperties(
    id: "orders",
    // 散ることのため、そしてすべての熱いクエリに入っているから選んだキーです。
    // 永久でもあります。変えるには新しいコンテナーと移行が要ります。
    partitionKeyPath: "/tenantId"));

// 単一パーティションの読み取り: キーを渡したので、1 つのパーティションが答えます。
var order = await container.ReadItemAsync<Order>(
    id, new PartitionKey(tenantId), cancellationToken: ct);
```

アクセスのパターンまで本当に時間の形をしている、時間の形のデータなら、SQL Server 自身のパーティションテーブルが、1 つの論理テーブルを範囲関数でパーティションに分けて保持します。するとアーカイブが削除ではなくメタデータの操作になります。

```sql
-- ログを埋める DELETE ではなく、スイッチで済ませる保存期間の運用です。
ALTER TABLE Telemetry SWITCH PARTITION 1 TO TelemetryArchive PARTITION 1;
```

目指す形は、シーンが終わる場所の形です。1 つの規則が行のありかを決め、その規則は 1 つの場所で読めて、すでにすべての熱いクエリが持ち歩いているものを指しています。パートは同じスキーマに違う行を持つか、同じ同一性に違う列を持つかで、そのどちらであるかは流れた結果ではなく決定でした。そして動いているシステムのどの部分も、パートの数が今日のままであることに寄りかかっていません。パーティショニングされたストアについて確かなことは 1 つ、いま持っている数より多くのパートが必要になるということだけです。
