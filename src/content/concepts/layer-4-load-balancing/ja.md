シーンの最初のステップで回っている順番も、どこかで回らなければなりません。そしてそれがどの層で起きるかが、バランサーに何を知ることが許されるかを決めます。L4 のバランサーはトランスポート層で働くので、入力は接続の 5 タプル、つまり送信元のアドレスとポート、宛先のアドレスとポート、プロトコルがすべてです。接続が開かれるときにバックエンドを一度選び、そのあとは転送の経路になります。バイト列は両方向に流れますが、バランサーはそれを解釈しないので、`GET /health` と 2 メガバイトのアップロードを区別できず、どちらがどれだけ掛かったのかも分かりません。

その見えなさが取引のすべてで、得るものは大きい側にあります。解釈するものがなければ溜めておくものもないので、接続ごとの仕事は表を引いてアドレスを書き換える程度です。カーネルの経路やハードウェアで動かせるほど安く、ありふれたマシンで何百万もの流れを抱えられます。解釈しないのでプロトコルも問いません。同じバランサーが SQL のポートも SMTP の中継もゲームサーバーも HTTPS のサイトも、どれがどれかを知らないまま前で受けますし、TLS をそのままバックエンドまで通せるので、証明書や秘密鍵がバランサーに置かれることもありません。戻りのトラフィックがアドレスを書き換えてバランサーを再び通るのか、バックエンドからクライアントへ直接返るのかはデプロイの話で、後者が存在するのはたいてい出ていく側のほうが太いからです。

代償は一文ですが、そこから続く帰結は長いものです。分散の単位はリクエストではなく接続です。短い HTTP/1.1 の接続では接続 1 本がほぼリクエスト 1 件なので、この事実は隠れます。長生きする接続では丸見えになります。gRPC は HTTP/2 の接続を 1 本抱えてすべての呼び出しをその上に載せるため、L4 の一度の判断がそのクライアントの全呼び出しを最初に着いたバックエンドへ固定し、あとから増やしたレプリカはクライアントが接続し直すまで何も受け取りません。WebSocket もデータベースの接続プールもメッセージブローカーのチャネルも同じ振る舞いをします。ほかの損も同じ見えなさから出てきます。パスやヘッダーや Cookie で振り分けることはできず、失敗したリクエストを別のバックエンドへ送り直すこともできません。バランサーはリクエストというものを見たことがないからです。そしてバランサーは転送するトラフィックから健全性について何も学ばないので、別立ての probe に全面的に頼ることになります。その probe は HTTP の probe にもできますが、素の TCP 接続のままにされることも多く、すべての呼び出し元にエラーを返しているプロセスでもその検査は通ります。

このどれもが、この層を劣った選択にするわけではありません。違う選択というだけで、2 つの層は比べるものというより上下に重ねて使うのが普通です。前段の L4 バランサーが接続を複数の L7 プロキシへ散らし、そのプロキシがリクエストを散らす形です。トラフィックが HTTP でないとき、リクエストごとの解析こそ避けたい出費だと言えるほど量が多いとき、途中の何もクライアントが送ったものを読めてはならないときは、この層が合っています。判断をリクエスト単位で下す必要があるとき、そして前にある接続が長生きする種類のときは、1 つ上の層が合っています。スティッキーな振る舞いもここで挙げておく価値があります。この層では、頼まなくても付いてくるからです。
